## GPT

我看完题目和你自己的 memo 之后，基本赞同你的判断，而且我觉得可以把选题进一步收敛：如果目标是“黑客松里两天半做出一个能跑、能展示、评委一眼看懂、又不太同质化”的东西，我目前会优先考虑赛道三，其次是把赛道二极度缩小之后做一个垂直场景，赛道一反而最不建议。

你对赛道一的判断是比较准确的。题目虽然口头上说“形式不限”，但它其实已经把评委脑子里的典型答案提前写出来了：智能匹配、信用评价、AI 发帖。 这会产生一个非常明显的问题：十个队伍里可能五六个都在做“校园二手/失物 + embedding + LLM + 推荐”。这种题不是不能做，而是非常依赖产品完成度。如果你只是“做出来”，基本没优势；你得做到交互特别顺滑、数据闭环特别完整，甚至真的有校园用户数据，才可能突出。

而你们团队如果技术能力比较强，其实没必要去跟别人拼一个“AI + 校园信息平台”的前端 demo。你 memo 里说“同质化会很严重”，我认为这是赛道一最大的风险。

赛道二我觉得需要稍微修正一下你的评价：题目本身确实有点理想化，但它没有真的要求你做“AI 接管整个人生”。它其实给你留了一个非常重要的逃生口——“你可以选择其中一个方向深入”，以及它强调的是长期画像、外部压力、事务负载、精力曲线。

真正危险的是，如果参赛者照着题目字面去做：

“读取邮件 + 读取微信 + 日历 + 情绪识别 + 长期记忆 + 自动规划 + AI 陪伴”

那两天半必炸。

但如果把它压缩成一个非常明确的学生场景，反而可能挺好。比如你 memo 里提到的“根据培养方案、课表、历史选课和个人目标给下一学期选课建议”，这个思路其实比原题里的“大而全规划助手”靠谱很多。

甚至可以继续压缩成一个更适合 demo 的东西：

“期末周 AI 作战室”。

用户只需要导入：
课程表、考试时间、DDL、课程资料量。

系统维护四个变量：
剩余天数、课程难度、剩余工作量、用户历史完成速度。

然后每天重新计算：

今天最应该干什么；
每件事建议做多久；
如果今天摆烂两小时，后面的计划怎么自动重排；
哪些任务已经进入风险区。

这个东西的好处是，你不需要假装“理解用户全部人生”，但又精准命中了赛道二说的“外部压力 + 并行事务负载 + 动态规划”。而且非常容易现场演示：

今天 9 月 4 日 → 离考试还有 7 天 → 当前安排。

然后人为制造一个事件：

“我今天晚上突然有社团活动，少了 3 小时。”

系统重新规划。

这个 demo 是成立的。

但是如果让我选，我依然更倾向赛道三。

因为赛道三的题目其实比前两个更“黑客松”。它没有要求你做一个成熟 SaaS，而是在问一个很明确的问题：

Agent 现在能写很多东西了，但是人怎么知道它到底干了什么？

而且这里有一个非常关键的点：

不要做“Multi-Agent Framework”。

这个坑你 memo 已经隐约意识到了——企业都在做，多 Agent orchestration 本身也很复杂，测试验证很困难。

如果你们去做：

Agent A planner
Agent B coder
Agent C reviewer
Agent D tester

最后搞个流程图。

我反而觉得大概率很普通。

因为这就是一个缩小版 LangGraph / CrewAI / AutoGen。

真正值得做的是赛道三里最核心的那句话：

“人在 Agent 的工作里怎么重新获得控制权？”

我现在最推荐你考虑一个方向：

Agent Change Inspector。

也就是“AI 改代码之后，人到底怎么快速验收”。

赛题自己已经举了“改动翻译器”的例子，但我会把它进一步做成一个完整产品，而不是三句话总结。

想象这个界面：

左边是 Agent 当前任务：

“给 FastAPI 项目增加登录鉴权。”

Agent 修改了 12 个文件、438 行代码。

普通用户看到 diff 基本已经放弃了。

你们系统不直接展示 438 行，而是生成一个“变更地图”：

Authentication
→ 新增 JWT 登录

Database
→ users 表增加 password_hash

API
→ /login 新增接口

Middleware
→ 增加 auth dependency

然后每一个模块显示：

为什么改；
改了哪些文件；
潜在风险；
怎么验证。

甚至再加一个非常强的功能：

“给我一个最小验证动作”。

比如系统告诉人：

要确认这次修改没问题，只需要做三件事：

1. 未登录访问 `/profile` 应返回 401；
2. 正确密码登录应返回 token；
3. 错误密码不能返回 token。

然后你点：

Run Verification。

系统执行测试。

这样你们做的已经不是“AI 帮你写代码”，而是：

AI 帮人理解 AI 做了什么。

我觉得这个命题非常符合赛道三，而且技术难度在两天半是可控的。

更关键的是，这个东西现场 demo 极其好演。

第一幕：

让 Claude Code / Codex / 任意 Agent 改一个项目。

第二幕：

屏幕上出现：

17 files changed
+623
-184

然后问评委：

“你敢直接点 Accept 吗？”

第三幕：

打开你们的系统。

它变成：

3 个功能变更
2 个潜在风险
4 个验证步骤

这一下产品价值就非常直观。

而且这个项目还可以加一个很有意思的设计，我觉得甚至可能成为你们的核心创新：

“Decision Checkpoint”。

Agent 不是所有东西都自动做。

系统自动识别“高影响决策”。

比如：

换数据库 schema；
删除 API；
修改鉴权；
换依赖版本；
大规模重构。

这些地方 Agent 必须停下来问人：

“这是一个不可逆/高影响修改，你需要选择 A / B。”

这样就真正对应了赛题里的：

“人在哪里看、在哪里拍板”。

而且你甚至不需要真的控制 Claude Code 内核。

完全可以：

Git diff
→ parser
→ LLM 分析
→ 风险分类
→ UI
→ test runner

技术架构很简单。

我甚至觉得你们还可以把赛道三另外一个“贡献归因 Attribution”融进来，但不要作为主功能。

例如项目结束以后自动生成：

Human Decisions：7

Agent Decisions：23

Human Overrides：4

Critical Decisions：3

然后时间轴展示：

10:32 Agent 建议换 SQLite → PostgreSQL
10:35 Kevin 拒绝
10:36 保留 SQLite

11:12 Agent 删除旧 API
11:14 Kevin 恢复兼容接口

这样最后可以生成一个：

“Human Contribution Report”。

这就自然覆盖赛题三的第四个方向，而不是硬做一个“贡献统计器”。

所以我现在会给三个赛道这样排序：

第一选择：赛道三
做 Human-in-the-loop，而不是 Multi-Agent Framework。

第二选择：赛道二
但必须缩成一个极具体的学生场景，比如“期末周动态规划器”。

第三选择：赛道一
除非你们有一个非常独特的机制，否则很容易变成另一个 AI 校园平台。

如果是我现在坐在你们队里，我甚至会直接把题目暂定成：

“AgentScope —— 让人看得懂 Agent 到底改了什么。”

核心 MVP 只做四件事：

Git diff 自动分析 → 变更语义化 → 风险提示 → 最小验证方案。

如果时间还有余量，再做：

Human Decision Checkpoint
和
Contribution Timeline。

这已经非常像一个完整黑客松作品了，而且最重要的一点是：两天半真的有可能做完。

相比之下，“做一个聪明的 Multi-Agent 协同平台”这种题，听起来很厉害，但非常容易最后变成四个 Agent 在终端里互相发 JSON，展示效果反而很差。

目前竞赛还提供了一个选择，就是自由赛道，可以自己去做想做的东西

我们组目前有个想法就是模仿 脑容量 里面的做法

然后依赖国内知乎提供的接口，结合类似的回答去给出相应的建议

### GPT 回答

这个方向我觉得“有潜力，但要改一下叙事和实现方式”，否则很容易变成“知乎答案总结器”。

我看了你同学这个《脑容量》提案，核心其实不是“调用知乎接口给建议”，而是想把三类东西拼起来：

历史人物 = 已经走完的人生样本
知乎 = 正在发生的人生样本
用户自己 = 正在选择的人生

然后系统不是直接告诉用户“你该考研/工作”，而是展示不同路径、对应代价、可能后悔什么。这个产品定位其实比普通 AI 建议工具高一层。

我觉得这里最有价值的点有三个。

第一，是“建议必须附带代价”。

比如它提到：

读博可能获得思想自主、专业身份，但付出延迟收入、结果不确定、社会比较压力；工作可能获得财务独立、真实世界反馈，但会减少深度研究时间，也更快形成路径依赖。

这个比“AI告诉你应该选什么”好很多。因为人生类问题本来就很难有唯一正确答案，真正有价值的是：

“你愿意承担哪一种代价？”

这个逻辑很适合做黑客松 Demo。

第二，是“同时代样本”这个概念挺好。

例如用户问：

“25 岁读博还是工作？”

系统不是只搜一个知乎高赞回答，而是搜一组经历：

直接工作
读博继续科研
读博后转行业
中途退出

然后分别抽取这些路径里最常见的：

后悔、满足、意外、成本。

提案第 11–12 页其实已经把这个方向讲得比较清楚了。

这就比简单 RAG 强，因为你们不是：

> 搜知乎 → LLM总结。

而是在做：

> 搜很多人生经历 → 分类成路径 → 提取结果与代价 → 再结合用户特征做对照。

这个产品逻辑是成立的。

第三，是“人生参照”比“人生预测”安全也合理。

提案里面“平行人生”的措辞我觉得处理得不错，它明确说不是预测，而是 Possible Selves，也就是“可能自我”。

这点非常重要。

因为你们千万不要 Demo 成：

> “根据知乎 100 个样本，你读博后悔概率 63%。”

这种看起来很数据科学，其实逻辑完全站不住。

知乎样本有巨大的 selection bias：

愿意发帖的人≠普通人
高赞回答≠代表性样本
“后悔读博”的问题下面天然会聚集负面经历
不同年份、专业、学校、城市、家庭情况完全不同

所以知乎数据适合做：

“有人这样走过。”

不适合做：

“你大概率会这样。”

这会决定你们项目是有思想，还是只是一个包装得比较漂亮的搜索器。

我甚至建议把知乎在产品里面的定位从：

“数据”

改成：

“案例库 / 人生样本库”。

比如不要写：

“43% 的人选择直接工作。”

而写：

“我们找到 43 个较相关的直接工作案例。”

这两个表述差别很大。

前者看起来像统计结论，后者只是案例数量，更严谨。

```text
案例 C

直接工作

路径
收益
代价
代表案例
适合什么样的人
你需要回答自己的问题
```

这样我就觉得这个项目很完整了。

而且两天半能做。

它现在提案里包括：

MBTI、历史人物、人生母题、未来人生、人生墓志铭、人生分叉、人生考古、精神家谱……

作为长期产品当然可以，但如果黑客松真做，我会毫不犹豫砍掉 80%。

你们就做一个核心 Demo：

> “一次重大选择的人生参照。”

提案最后第 14–15 页本身其实已经给了非常好的 Demo 结构：

用户提出困境
→ AI追问真正害怕什么
→ 重构问题
→ 历史样本
→ 同时代知乎样本
→ 平行未来
→ 选择自己愿意承担的遗憾。

这已经够打比赛了。

我甚至建议把历史人物都先弱化。

因为历史人物其实有一个问题：

很容易变得很文学，但缺乏实际决策价值。

真正实用的是：

“一个和我背景差不多、三年前面临同样选择的人后来怎么样？”

所以如果只有两天半，我会把资源投入排序变成：

知乎真实案例 ＞ 用户画像 ＞ 决策路径分析 ＞ 历史人物。

历史人物可以只是一个“彩蛋式”展示。

但这个方案目前最大的风险，其实不是 AI。

是：

**知乎接口。**

你同学说“依赖知乎提供的接口”，我会先让他确认一件事：

**Experience Source**

而不是：

**产品 = 知乎 API 外壳。**

这一点我会特别强调。

---

如果是我来给这个作品重新包装，我甚至不会说：

> “我们利用知乎给你人生建议。”

这个听起来特别像：

“知乎搜索 + ChatGPT 总结”。

我会说：

> **我们正在构建一个 Human Experience Retrieval System。**

传统搜索回答的是：

> “别人怎么说？”

而你们回答：

> “和我情况相似的人，分别走过哪些路？他们得到了什么，又付出了什么？”

这个故事一下就高级很多。

甚至技术层面也能有一个不错的亮点：

不要只做普通 Embedding Retrieval。

可以定义一个 Experience Schema：

```json
{
  "background": {
    "age": 24,
    "education": "本科",
    "major": "CS"
  },
  "decision": "读研 vs 工作",
  "chosen_path": "直接工作",
  "motivation": [
    "经济独立",
    "不喜欢科研"
  ],
  "outcome": [
    "进入互联网公司",
    "三年后晋升"
  ],
  "benefits": [
    "工程经验",
    "收入"
  ],
  "costs": [
    "学历限制",
    "研究机会减少"
  ],
  "regrets": [
    "没有体验研究生活"
  ],
  "time_horizon": "3年"
}
```

LLM负责把知乎自然语言回答转换成这个结构。

然后真正检索的时候，不是：

```text
query → embedding → topK
```

而是：

```text
用户画像
+
人生选择
+
风险偏好
+
约束

↓

Experience Matching

↓

最相关人生样本
```

这其实已经是一个挺不错的技术点了。

我会给它一个名字：

**Life Experience Retrieval**

甚至可以说是：

**RAG for Decisions，而不是 RAG for Facts。**

传统 RAG：

```text
Question
↓
Facts
↓
Answer
```

你们：

```text
Decision
↓
Similar Experiences
↓
Possible Paths
↓
Trade-offs
↓
Reflection
```

这个区别非常适合放答辩 PPT。

所以我的判断是：

**选题本身值得做，我会给 8/10。**

但如果只是：

> 输入问题 → 调知乎 → LLM总结 → 给建议

大概只有 **5/10**。

如果升级成：

> 用户画像 → 人生冲突识别 → 真实经历检索 → 路径聚类 → 收益/代价抽取 → 相似人生匹配 → 平行路径展示
