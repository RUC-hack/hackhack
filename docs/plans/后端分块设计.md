# 后端分块设计

Kevin  
2026-09-04

## 一、目标与技术基线

本设计把现有产品架构和 [问答设计 XAI](../问答设计XAI.md) 落成一套能够在一个开发日内完成的后端模块边界。

技术基线：

- 继续使用 Node.js ESM 和 `.mjs`，不在比赛中途迁移语言；
- MVP 优先使用 Node.js 标准库，新增第三方依赖必须先说明用途；
- 前端只能访问本项目 HTTP API，不能直接访问知乎或大模型；
- Agent 是有状态的单 Orchestrator，不搭建多 Agent 框架；
- JSONL/文件存储满足单机演示，暂不引入数据库和向量库；
- OAuth、SSE、历史人物库和推测性提前检索均不属于明日必做。

最终纵向闭环：

```text
前端提交消息
  -> HTTP API 校验
  -> SessionService 保存原始消息
  -> Orchestrator 决定 ask / retrieve / respond / confirm_topic / safety
  -> RetrievalService 调用 Zhihu 或 LocalDataset
  -> EvidenceService 保存和审核材料
  -> AnswerBuilder 生成有来源的动态回答
  -> SessionStore 保存状态
  -> 返回统一响应并记录脱敏日志
```

## 二、分块总览

| Block | 名称 | 核心职责 | 依赖 | 明日级别 |
|---|---|---|---|---|
| `B0` | Contracts & Errors | 稳定 DTO、错误码、校验器 | 无 | 必须 |
| `B1` | Config & Composition | 环境、实例装配、启动检查 | B0 | 必须 |
| `B2` | HTTP API | 路由、请求校验、响应外壳、取消 | B0、B1 | 必须 |
| `B3` | Session & State | 会话、消息、上下文版本、状态迁移 | B0 | 必须 |
| `B4` | LLM Gateway | 大模型调用和结构化输出校验 | B0、B1 | 必须 |
| `B5` | Orchestrator | 单轮决策和状态流程 | B0、B3、B4 | 必须 |
| `B6` | Retrieval | Query、Provider、缓存、降级 | B0、B1 | 必须 |
| `B7` | Evidence | 来源保存、证据生命周期、引用校验 | B0、B3、B6 | 必须 |
| `B8` | Answer | 动态 sections、限制说明、来源绑定 | B0、B4、B7 | 必须 |
| `B9` | Storage & Logs | Session/Source 存储、脱敏审计日志 | B0 | 必须 |
| `B10` | Safety | 风险分流、注入隔离、凭证脱敏 | B0、B5 | 必须的最小版 |
| `B11` | Tests & Fixtures | 单元、契约、集成、冒烟 | 全部 | 必须 |

依赖方向只能由上层指向下层接口；Provider、LLM 和 Store 必须可通过构造器替换，测试不得靠修改全局状态切换实现。

## 四、各分块详细设计

### B0：Contracts & Errors

只固定技术契约，不固定人生经历的语义分类。

稳定对象：

- `Session`：会话 ID、状态、上下文版本、原始消息、检索记录、当前回答；
- `SourceDocument`：来源、标题、作者、纯文本摘要、URL 和检索时间；
- `EvidencePacket`：原始摘要、开放 observations、unknowns、证据引用；
- `AgentDecision`：控制动作和简洁解释；
- `AnswerEnvelope`：动态 sections、assumptions、unknowns、limitations；
- `AppError`：稳定 `code/status/retryable/details/cause`。

统一 HTTP 外壳：

```json
{
  "ok": true,
  "data": {},
  "error": null,
  "request_id": "req_..."
}
```

失败时：

```json
{
  "ok": false,
  "data": null,
  "error": {
    "code": "SESSION_NOT_FOUND",
    "message": "Session does not exist",
    "retryable": false
  },
  "request_id": "req_..."
}
```

规则：错误响应不返回堆栈、Secret、上游完整响应或模型原始 Prompt。

### B1：Config & Composition

职责：

- 一次性读取 `.env.local`；
- 解析为冻结的 runtime config；
- 创建 Logger、Store、LLM、Providers、Services 和 HTTP Server；
- 提供 `startServer()` 与 `createApp(overrides)`；
- 启动时检查目录可写性，但不在默认启动中调用外部 API。

产品模式：

| 模式 | Primary | Fallback | 外部调用 |
|---|---|---|---|
| test | MockProvider | 无 | 禁止 |
| development | LocalDatasetProvider | 无 | 默认禁止 |
| live | ZhihuProvider | LocalDatasetProvider | 显式允许 |

### B2：HTTP API

MVP 路由：

| 方法 | 路径 | 输入 | 输出 |
|---|---|---|---|
| GET | `/api/health` | 无 | 服务和 Provider 状态 |
| POST | `/api/sessions` | 可选初始问题 | 新会话快照 |
| GET | `/api/sessions/:id` | 会话 ID | 会话可公开状态 |
| POST | `/api/sessions/:id/messages` | 用户消息、可选客户端 turn ID | 本轮动作或回答 |
| GET | `/api/sources/:id` | 来源 ID | 来源摘要和 URL |

边界：

- 请求体默认不超过 64 KiB；
- 只接受 `application/json`；
- CORS 使用显式允许来源；
- 每个请求创建 `request_id` 和 `AbortController`；
- API 层不直接调用知乎或 LLM；
- 同一 `client_turn_id` 重复提交时返回同一结果，避免浏览器重试产生重复检索。

SSE 只有 REST 主流程稳定后再增加，不作为明日完成条件。

### B3：Session & State

核心状态采用 XAI 文档版本：

```text
COLLECTING_CONTEXT
READY_FOR_RETRIEVAL
RETRIEVING
REVIEWING_EVIDENCE
PRESENTING
WAITING_FOR_FOLLOW_UP
CONFIRMING_TOPIC
SAFETY_HANDLING
FAILED_RECOVERABLE
```

关键不变量：

- 原始消息只追加，不覆盖；
- 模型推断和用户原话分开；
- 每次问题理解改变时递增 `context_version`；
- 旧检索记录保留，但必须变成 `stale` 或重新验证；
- 追问预算耗尽后给暂定回答，不进入无限循环；
- 每次消息只执行一次状态推进，不在 HTTP 请求中运行无界 while loop。

### B4：LLM Gateway

LLM Gateway 只提供两个稳定能力：

```text
decideNextAction(sessionView, signal) -> AgentDecision
buildGroundedAnswer(answerInput, signal) -> AnswerEnvelope
```

要求：

- Prompt 与模型参数由独立文件或函数管理；
- 模型返回 JSON 必须先解析、校验，再允许调用工具；
- `action=retrieve` 才读取 queries；
- 未知 source ID、非法 action、超长输出或非 JSON 进入可恢复错误；
- 测试使用 FakeLLM，CI 不调用真实模型；
- 最多进行一次格式修复，不进行无限自修复循环。

### B5：Orchestrator

Orchestrator 是领域流程控制器，不负责 HTTP、文件读写细节或知乎字段转换。

单轮算法：

```text
接收用户消息
  -> SafetyService 检查特殊流程
  -> SessionService 追加原始消息
  -> 识别直接回答、跳过、切题和否定假设等意图
  -> LLM Gateway 生成 AgentDecision
  -> 校验动作与当前状态是否合法
  -> ask：保存问题并返回
  -> retrieve：生成检索记录并调用 RetrievalService
  -> respond：只基于已验证 Evidence 构建回答
  -> confirm_topic / safety：进入专用状态
```

Orchestrator 必须由明确的状态转移表约束，LLM 不能直接修改整个 Session。

### B6：Retrieval

沿用现有三层边界：

```text
RetrievalService
  -> ZhihuProvider
       -> ZhihuSearchClient
  -> LocalDatasetProvider
  -> MockProvider
```

统一接口：

```text
provider.search(query, options) -> {
  documents: SourceDocument[],
  meta: RetrievalMeta
}
```

必须完成：

- 修复 [问题登记册](../issues/README.md) 中 `BE-001/002/005/006/007/008/009/010/011`；
- Provider 合同测试；
- 相同缓存键 in-flight 合并；
- 知乎不可用时真实装配 LocalDatasetProvider；
- 空结果可以按策略尝试下一条 query，但全局调用数必须有预算上限。

### B7：Evidence

处理顺序：

1. 原样保存 `SourceDocument`；
2. 针对当前问题提取有依据的观察；
3. 保存原始证据片段和 `source_id`；
4. 标记 `candidate / validated / used / stale / rejected`；
5. 不可分类材料继续保留。

EvidenceService 必须验证：

- 证据片段能在纯文本摘要中找到；
- 所有 source ID 已存在；
- 摘要不足时只能生成 unknown，不补写动机、背景或结局；
- 检索材料中的指令永远作为数据，不作为 Prompt 指令执行。

### B8：Answer

输出只固定最小渲染外壳：

```json
{
  "summary": "当前综合",
  "sections": [],
  "assumptions": [],
  "unknowns": [],
  "limitations": [],
  "next_actions": []
}
```

`sections[].kind` 可以动态变化。后端校验以下不变量：

- 引用知乎观点的 section 必须有有效 source ID；
- 用户信息引用对应 message ID；
- 不输出成功概率或把知乎样本描述为总体统计；
- 必须说明摘要和样本偏差；
- 未知 kind 仍有纯文本 fallback 内容。

### B9：Storage & Logs

MVP 使用文件和内存的组合：

- `MemorySessionStore`：测试和单进程快速读取；
- `JsonlSessionStore`：演示环境持久化追加事件；
- `SourceStore`：按 source ID 保存来源；
- `AuditLogger`：保存脱敏操作事件。

推荐统一路径：

```text
logs/conversations/YYYY-MM-DD/session-<id>.jsonl
logs/zhihu/YYYY-MM-DD/request-<id>.jsonl
.runtime/cache/zhihu/<cache-key>.json
```

日志写入失败默认不覆盖业务错误。真实对话和真实检索日志不进入 Git；只提交匿名 fixtures。

### B10：Safety

明日只实现最小且可测试的安全边界：

- 普通迷茫继续主流程；
- 明显痛苦减少追问强度；
- 可能即时风险进入 `SAFETY_HANDLING`，不继续知乎检索；
- 拒绝输出 Secret、Token、环境变量和系统 Prompt；
- 用户正常询问 API 用法不应被误拦截；
- 知乎材料和用户内容都视为不可信数据。

安全模块返回分类和用户可见策略，不直接修改 Session 文件。

### B11：Tests & Fixtures

测试分层：

| 层级 | 是否联网 | 目标 |
|---|---:|---|
| unit | 否 | 纯函数、状态迁移、校验、脱敏、缓存 |
| contract | 否 | API、Provider、LLM structured output 契约 |
| integration | 否 | 从创建会话到生成有来源回答的完整流程 |
| quality | 否 | 多样输入和 XAI 不变量 |
| smoke | 显式允许 | 知乎与 LLM 各一次最小握手 |

CI 默认只执行前四层。Smoke 必须同时提供凭证、`ALLOW_LIVE_EXTERNAL_CALLS=true` 和 `--live`。

## 五、模块间数据流

### 追问轮

```text
POST message
  -> append raw message
  -> AgentDecision(action=ask)
  -> validate decision
  -> persist state transition
  -> return question + reason + controls
```

### 检索与回答轮

```text
POST message
  -> AgentDecision(action=retrieve, queries=[...])
  -> enforce query budget
  -> RetrievalService
  -> SourceStore
  -> EvidenceService
  -> AnswerBuilder
  -> validate all citations
  -> persist answer
  -> return AnswerEnvelope
```

### 降级轮

```text
ZhihuProvider classified failure
  -> RetrievalService catches allowed code
  -> LocalDatasetProvider
  -> meta.degraded=true
  -> answer limitations mention local fallback
```

## 六、明日后端完成定义

同时满足以下条件，才称为“后端完成”：

- 五个 MVP HTTP 路由可调用；
- 从创建会话到追问或生成回答的纵向流程可运行；
- Mock、Local、Zhihu 三个 Provider 契约一致；
- 知乎失败能够实际降级，不只是留下接口；
- 回答中的所有知乎观点可以回查 source ID；
- 用户原话和模型推断不混淆；
- 不出现无限追问或无限模型修复；
- 日志和响应不泄露凭证；
- 离线单元、契约、集成测试全部通过；
- 显式运行的最小知乎和大模型 smoke 通过，或留下清楚的外部阻塞记录；
- 所有改动先由用户审查，未经明确要求不提交、不推送。
