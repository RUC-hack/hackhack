## 一、执行目标

明日目标不是把所有长期功能都写出来，而是完成一个可演示、可降级、可测试的后端纵向闭环：

```text
创建会话
  -> 用户发送问题
  -> 系统追问或决定检索
  -> 知乎 / 本地案例检索
  -> 保存来源和证据
  -> 生成有出处、有局限说明的回答
  -> 前端可通过 HTTP 获取结果
```

实施依据：

- [后端分块设计](./后端分块设计.md)
- [后端问题登记册](../issues/README.md)
- [问答设计 XAI](../问答设计XAI.md)
- [项目结构](../项目结构（初稿）.md)

## 二、范围冻结

### 明日必须完成

- 修复 P1 及主流程涉及的 P2 问题；
- 稳定 Contracts、错误体系和配置；
- Mock、Local、Zhihu Provider；
- 单会话状态、逐轮 Orchestrator；
- LLM 决策与回答两个结构化调用；
- 来源、证据和最小文件存储；
- 五个 REST API；
- 单元、契约和离线集成测试；
- 显式的知乎/LLM 最小 smoke 命令；
- 能被现有前端接入的示例请求和响应。

### 明日不做

- OAuth 登录；
- 多 Agent 框架；
- 向量数据库、PostgreSQL 或复杂迁移；
- 提前推测性检索；
- SSE，除非 REST 全部完成且仍有余量；
- 多用户鉴权、云部署和生产级扩缩容；
- 历史人物、MBTI、长期画像等扩展产品功能；
- 基于知乎样本计算成功率或人生预测。

## 三、生成顺序与检查点

每一阶段都采用“小块生成 → 运行测试 → 查看 diff → 人工审查”的方式。不得一次生成整个后端后才开始测试。

### Phase 0：冻结契约

产物：

- `contracts/errors.mjs`
- `contracts/source-document.mjs`
- `contracts/session.mjs`
- `contracts/evidence.mjs`
- `contracts/answer.mjs`
- 对应 contract tests

完成条件：

- DTO 只固定技术字段；
- 未知 section kind 可保留；
- 用户原话与模型推断字段分离；
- API 错误码和 HTTP 状态映射确定。

检查点 C0：先审查契约，再让其余模块依赖这些对象。契约未确认前不批量生成服务代码。

### Phase 1：加固现有知乎检索

处理：

- `BE-001/002/005/006/007/008/009/010/011/013/015`；
- 保持 `ZhihuSearchClient -> ZhihuProvider -> RetrievalService` 分层；
- 增加 LocalDatasetProvider 和 MockProvider；
- 增加 Provider 合同测试和并发测试。

完成条件：

- 错误分类稳定；
- 相同 query 并发只调用一次上游；
- 日志/缓存失败不掩盖原错误；
- 取消信号可以到达 fetch；
- 三个 Provider 返回同一最小结构；
- 断网、限流、未配置凭证均能降级。

检查点 C1：运行 retrieval 全部测试并单独审查外部调用、Secret 和文件写入路径。

### Phase 2：Storage 与日志

产物：

- MemorySessionStore
- JsonlSessionStore
- SourceStore
- AuditLogger 与 redaction helper

完成条件：

- Session 事件追加保存；
- Source 可按 ID 回查；
- 日志按日期组织；
- Secret、Token、authorization code 和敏感字段脱敏；
- 日志失败策略有测试；
- 重启后至少能恢复演示会话的公开快照。

检查点 C2：使用含假 Secret 的 fixture 扫描所有日志，断言原值不存在。

### Phase 3：Session 与 Orchestrator 骨架

先用 FakeLLM 和 MockProvider 打通状态，不等待真实模型接入。

产物：

- SessionService
- 状态转移表
- AgentOrchestrator
- SafetyService 最小版

完成条件：

- 一条消息只推进一次状态；
- 支持 `ask/retrieve/respond/confirm_topic/safety`；
- 支持跳过、立即回答、切题和否定假设；
- 追问预算耗尽后给暂定结果；
- 旧上下文证据不会自动进入新话题。

检查点 C3：状态测试全部通过后再接入真实 LLM。

### Phase 4：LLM Gateway

产物：

- LLM Client
- Decision Prompt
- Answer Prompt
- AgentDecision 校验器
- AnswerEnvelope 校验器
- FakeLLM fixtures

完成条件：

- 模型输出未校验前不执行工具；
- 非 JSON、非法 action、虚假 source ID 可恢复；
- 只允许一次格式修复；
- 超时与取消有稳定错误码；
- Prompt 不包含 Secret，检索内容用明确数据边界包裹。

检查点 C4：使用固定 FakeLLM 输出完成 ask、retrieve、respond 和非法输出四类测试。

### Phase 5：Evidence 与 Answer

产物：

- EvidenceService
- AnswerBuilder
- 来源引用校验
- 动态 section fallback

完成条件：

- 原始摘要先保存，分析结果不能覆盖它；
- 证据片段可回到 source ID；
- 无法分类案例不会丢失；
- 回答明确材料限制；
- 不输出伪概率或把知乎当总体；
- 本地降级时在 limitations 中说明来源变化。

检查点 C5：用至少三种不同叙事结构验证输出，不断言固定栏目数量。

### Phase 6：HTTP API 与 Composition Root

产物：

- `app.mjs`
- HTTP Server、Router、Request Parser
- Health、Session、Message、Source 路由
- 启动命令和 API 示例

完成条件：

- 前端不接触任何外部 Secret；
- 请求体限制、Content-Type、CORS、404 和错误外壳有效；
- `request_id` 贯穿日志和响应；
- `client_turn_id` 支持幂等；
- HTTP 取消信号传入 Orchestrator；
- 所有路由使用相同 Composition Root。

检查点 C6：通过离线 HTTP 集成测试完成一次创建会话到回答的纵向流程。

### Phase 7：Smoke 与交付检查

顺序：

1. 全部离线测试；
2. 环境 Doctor；
3. 本地 Provider 完整演示；
4. 显式运行一次大模型 handshake；
5. 显式运行一次知乎最小查询；
6. 模拟知乎失败，确认本地 Provider 接管；
7. 扫描日志与响应，确认无凭证；
8. 检查 Git diff 和未跟踪文件。

检查点 C7：向用户提供变更摘要、测试结果和待审问题；不自动提交或推送。

## 四、代码约定

### 4.1 语言与模块

- Node.js ESM；
- 使用 `.mjs` 和显式相对路径扩展名；
- 优先标准库；引入依赖必须同步更新 `package.json`、锁文件和文档；
- 不在明日进行 TypeScript、CommonJS 或 Python 迁移；
- 不从 `experiments/` 或 `zhihu-hackathon/assets/` 导入产品运行时代码。

### 4.2 命名

- JS 函数、变量、options 使用 `camelCase`；
- 类使用 `PascalCase`；
- 文件使用 `kebab-case.mjs`；
- 环境变量使用 `UPPER_SNAKE_CASE`；
- HTTP JSON 和稳定 DTO 沿用设计文档中的 `snake_case`；
- 只允许在 API/Provider adapter 边界转换命名，不在业务层随意混用。

### 4.3 模块边界

- Route 只负责 HTTP 转换，不包含业务判断；
- Orchestrator 只决定流程，不直接读写文件或拼接知乎 URL；
- Provider 只产生来源，不生成最终建议；
- AnswerBuilder 只使用已保存、已验证的 Evidence；
- Store 不理解 Agent 语义，只保存稳定对象和事件；
- Logger 不改变业务结果；
- Integration Client 不依赖 Session 或前端对象。

### 4.4 依赖注入

以下依赖必须可注入：

- `fetch`；
- `now()`；
- `randomUUID()` 或 ID factory；
- `sleep()`；
- Provider；
- LLM Gateway；
- Store；
- Logger。

测试不得真实等待、真实联网或依赖本机日期。

### 4.5 异步、超时和取消

- 所有外部调用必须有超时；
- `AbortSignal` 从 HTTP 层一路透传；
- 用户取消不重试；
- 业务码 `30001` 不重试；
- 网络失败和 `90001` 只允许有限、带预算的重试；
- 同一缓存键使用 single-flight；
- 不创建无界后台 Promise，不在一次请求中执行无界循环。

### 4.6 错误约定

- 预期错误必须使用 `AppError` 子类或稳定 code；
- 不按错误 message 做程序判断；
- 包装错误时保留 `cause`；
- API 对外隐藏堆栈和内部 details；
- fallback 失败时同时保留 primary/fallback 错误上下文；
- 文件系统错误必须被分类，不能意外覆盖领域错误。

### 4.7 数据与 Schema

- Schema 只固定系统执行所需字段，不限制人生经历主题；
- 原始消息和原始来源只追加、不覆盖；
- 模型推断必须标记 `assistant_inference/tentative`；
- 未知信息进入 `unknowns`，不得猜测补齐；
- 所有知乎观点必须能追溯到 source ID；
- API 的 `summary` 是纯文本，不允许未经清洗的 HTML；
- 时间统一保存 ISO 8601 UTC，展示层负责本地化。

### 4.8 日志与隐私

- 每条事件包含 schema version、request ID、可用时的 session ID、阶段、时间和耗时；
- 不记录 Access Secret、API Key、OAuth Token、authorization code、完整环境变量；
- 真实对话默认不提交 Git；
- 查询哈希只视为伪匿名标识；需要跨请求关联时使用本地 HMAC；
- 用户内容进入日志前必须经过字段级脱敏；
- 日志与缓存设置独立保留周期。

### 4.9 注释与文档

- 注释解释“为什么”和边界，不复述代码；
- 公开导出必须在模块 README 或 JSDoc 中说明输入、输出和错误；
- 新增或改变 API、环境变量、日志格式、状态机时同步更新文档；
- 重大架构决策新增 ADR，不把决定只留在聊天记录里。

### 4.10 文件规模

- 一个模块只承担一个主要职责；
- 文件明显超过约 250 行并继续增长时，优先按职责拆分；
- 不为了追求行数拆出没有语义的小函数；
- 公共 helper 只有在至少两个模块使用且语义稳定时才抽取。

## 五、测试约定

### 5.1 测试命名

```text
<module>.test.mjs
<feature>.contract.test.mjs
<flow>.integration.test.mjs
```

测试名称使用行为描述，例如：

```text
provider falls back to local data after Zhihu rate limiting
orchestrator stops asking when the user requests an immediate answer
answer rejects a source id that is not present in SourceStore
```

### 5.2 每个模块最低测试

- 正常路径；
- 参数或结构错误；
- 依赖失败；
- 超时或取消；
- 不变量；
- 不泄露凭证。

### 5.3 生成式测试

不比较整段自然语言是否逐字相等，验证：

- action 合法；
- 状态迁移合法；
- 来源存在且可追溯；
- 未分类内容仍保留；
- assumptions、unknowns 和 limitations 符合约束；
- 不含伪造来源、凭证和伪统计结论。

### 5.4 测试命令目标

计划补充：

```json
{
  "test": "运行全部离线测试",
  "test:unit": "只运行单元测试",
  "test:contract": "只运行契约测试",
  "test:integration": "只运行离线集成测试",
  "test:smoke": "默认 dry-run，不访问外部服务",
  "test:smoke:live": "显式执行最小外部握手"
}
```

具体命令以 Node 版本和最终目录为准，但默认 `npm test` 不得访问网络。

## 六、协作与审查约定

- 开始一个 Phase 前先确认前置契约；
- 不覆盖队友未审查的修改；
- 每个 Phase 结束后提供文件清单、行为变化、测试结果和已知风险；
- 生成代码后先运行格式、测试和 `git diff --check`；
- 不把格式化扩散到无关文件；
- 不修改真实 `.env` 或打印 Secret；
- 不用真实知乎响应覆盖 fixtures；
- 未经 Kevin 明确要求，不执行 `git commit` 或 `git push`；
- 发现设计冲突时先记录到 issue/ADR，再选择单一契约实现。

## 七、明日建议分工

可以并行，但必须遵循依赖边界：

| 工作流 | 内容 | 可并行条件 |
|---|---|---|
| A | Contracts、Errors、Config | 最先完成，其他人等待 C0 |
| B | Zhihu 加固、Local/Mock Provider | C0 后可独立进行 |
| C | Storage、Logs | C0 后可独立进行 |
| D | Session、State、Orchestrator | C0 后使用 FakeLLM/MockProvider |
| E | LLM Gateway、Prompts | C0 后独立开发 |
| F | HTTP API | 先用 Fake Services，C0 后进行 |
| G | Evidence、Answer | C0 后使用固定 fixtures |
| H | 集成、Smoke、前端联调 | B 至 G 汇合后进行 |

合并顺序以接口依赖为准，不以谁先写完为准。并行开发时通过 contract tests 防止各模块自行发明不同字段。

## 八、停止线与降级方案

如果时间不足，按以下顺序砍功能：

1. 取消 SSE；
2. 取消提前检索；
3. Evidence 提取使用一次模型调用，不做复杂二次聚类；
4. 持久化退化为 JSONL + 内存索引；
5. 真实知乎不稳定时固定使用 LocalDatasetProvider 完成演示；
6. 真实 LLM 不稳定时使用预置 FakeLLM 场景展示状态和来源闭环。

不得为了赶进度砍掉：来源追溯、凭证保护、本地降级、请求上限、状态终止条件和离线测试。
