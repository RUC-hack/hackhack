# 检索、模型与全链路实验总报告

> 日期：2026-09-05  
> 范围：截至本报告生成时仓库内已经执行的本地测试、知乎真实调用、DeepSeek 独立实验和服务端全链路实验。

## 结论先行

三层链路分别得到验证：

1. 知乎接口可以完成“query → 返回回答材料”：新额度下 8/8 真实调用成功、80 条结果全部满足接口 schema；在 4 个固定案例中，generated query 的 Top-5 usable precision 为 0.90，baseline 为 0.55。
2. DeepSeek 可以参与“材料筛选 → 证据约束回答”，但不能依赖一次裸 JSON 输出。`deepseek-chat` 最终四案例 selector 全部合法，和现有单评审标签比较的 precision/recall/accuracy 为 0.9474/1.0/0.95；原始答案 3/4 合法，确定性后处理后 4/4。
3. 真实 HTTP 全链路在引入宽容 JSON 提取和严格校验修复网关后通过 16/16：动作顺序 `ask → respond`，使用 2 条知乎 query，保存并回读 10 个来源，最终状态正确，重复提交保持幂等。

这不是“产品已经全部完成”：浏览器前端目前还没有调用后端 API，所以通过的是服务端交互链路，不是浏览器 UI 链路。浏览器验收方案见 `experiments/e2e-full-chain/browser-acceptance.md`。

## 0. 总体实验流程

```text
固定案例与验收规则
        ↓
知乎检索层：baseline query vs generated query
        ↓ 冻结 Top-5 结果
DeepSeek 层：selector 筛选 → writer 组织 AnswerEnvelope
        ↓ 验证模型与接口都可用
HTTP 全链路：用户首问 → 模型追问 → 用户补充 → 知乎检索
            → 证据包 → 模型回答 → 来源回读 → 幂等重放
```

各层分开计量：DeepSeek 独立实验不会再次调用知乎；全链路则使用新会话和真实外部服务。失败结果不删除，而是作为后续设计变更的证据。

## 1. 本地自动化测试

2026-09-05 执行 `npm test`：45 个测试全部通过，0 失败、0 跳过。覆盖 contract、HTTP、状态机、安全、缓存并发、Zhihu provider、持久化、旧 LLM gateway，以及新增的 JSON 平衡提取和严格网关。

新增的 5 个测试专门验证：

- 模型输出前后带说明或代码围栏时仍可提取完整 JSON；
- 截断 JSON 被稳定拒绝；
- 修复请求包含具体错误和上一版非法 JSON；
- 虚构 `source_id` 在进入 AnswerBuilder 前被修复；
- 修复次数有上限，不形成无限 loop。

## 2. 知乎检索实验

### 2.1 Oracle 先导与额度截断

原始 Oracle 计划执行 32 次，实际 HTTP transport 32/32 成功；业务成功 10 次、`Code=30001` 22 次。10 次成功响应全部 schema 合法，共返回 100 条材料、每次 10 条且无空结果。

限流首次在请求序号 5 出现，因此 31.25% 不能解释成接口固有可靠率；它混入了额度耗尽这一外部截断。能成立的结论只是：成功响应的结构质量为 10/10，旧额度不足以完成原计划。

### 2.2 旧额度下的失败复现

- baseline 累积原始文件含 9 次 `Code=30001`；用户现场一次批次输出为 8/8 限流，随后 resume 检查又记录 1 次。
- 首次低额度配对实验只执行 1 次即遇到 `30001`，按停止规则终止，0 个质量分母。

这组失败说明换请求参数或继续重试不能解除账号级额度限制，也促成了后续“交错、低调用量、遇限流即停”的设计。

### 2.3 新额度下的配对实验

设计：C01/C03/C05/C07 四个案例，每个案例比较用户原话 `baseline` 与预生成单 query `generated`；共 8 次，顺序预注册并交错，每次 `count=10`。

| 指标 | 总计 | baseline | generated |
|---|---:|---:|---:|
| 调用 | 8 | 4 | 4 |
| HTTP/业务/schema 成功 | 8 | 4 | 4 |
| 返回材料 | 80 | 40 | 40 |
| 空结果/限流/其他失败 | 0 | 0 | 0 |
| 平均延迟 | — | 608 ms | 870 ms |

总体延迟 p50 661 ms、p95/最大 1483 ms；实验前后额度从 5000 降到 4992，和 8 次调用一致。

### 2.4 Top-5 质量评分

每条材料按 relevance、lived experience、evidence sufficiency 各 0–2 分；三项都不低于 1 才记为 usable。

| 条件 | 标注 | usable | precision@5 | 平均相关性 | 平均个人经历 | 平均证据充分度 |
|---|---:|---:|---:|---:|---:|---:|
| generated | 20 | 18 | 0.90 | 1.90 | 1.60 | 1.85 |
| baseline | 20 | 11 | 0.55 | 1.70 | 0.90 | 1.45 |

逐案例 generated/baseline：C01 1.00/0.80、C03 0.80/0.40、C05 1.00/0.40、C07 0.80/0.60。该结果支持 query builder 在这四例中继续进入产品 loop，但样本很小，且标注是 `codex-single-rater` 的 model-assisted 单评审；尚无第二位独立评审和 Cohen's kappa。

## 3. DeepSeek 单独实验

### 3.1 设计

输入固定为上一节 generated 条件的 4×Top-5 材料，不再消耗知乎额度。每例运行两阶段：

1. selector 对每条候选判断相关性、个人经历、证据充分度和 usable，并给出选择理由；
2. writer 只能使用选中材料生成 `AnswerEnvelope`，所有材料性段落引用允许的 `source_id`，并禁止伪成功率。

主要门槛是 selector/answer schema、引用闭集、禁用统计措辞、和现有单评审标签的一致性、模型调用数、token 与延迟。

### 3.2 迭代结果

| 版本 | 模型/范围 | 成功案例 | selector 合法 | answer 合法 | 关键发现 |
|---|---|---:|---:|---:|---|
| v1 | v4-flash，4 例 | 0/4 | 0.25 | 0 | 只接受整段纯 JSON 太脆弱 |
| v2 | v4-flash，4 例 | 1/4 | 0.75 | 0.25 | 单次修复仍缺具体错误上下文 |
| v3 | v4-flash，4 例 | 2/4 | 0.75 | 0.50 | 保存 raw content 后可区分解析与契约失败 |
| v3 targeted | deepseek-chat，C03/C07 | 2/2 | 1.00 | 1.00 | chat 模型和短提示显著更稳定 |
| v3 full | deepseek-chat，4 例 | 3/4 | 1.00 | 0.75 | selector 稳定；writer 仍需确定性 guardrail |
| v3 recovered | 离线规范化 | 4/4 | 1.00 | 1.00 | 0 次额外模型调用；不是原始合规率 |

最终四例原始运行共 12 次模型调用、34,454 tokens、平均模型调用延迟 4,058 ms。selector 对 20 个候选的混淆矩阵为 TP=18、FP=1、FN=0、TN=1，precision=0.9474、recall=1.0、accuracy=0.95。

唯一原始失败 C07 的首次 answer 把 `limitations` 输出成字符串，并在 unknowns 中使用“二战成功率”；修复后数组结构正确，但仍保留禁用措辞。离线恢复只做可审计的字段数组化和中性措辞替换，没有增加新事实。

因此推荐的可复用形态不是“直接相信模型 JSON”，而是：宽容提取 JSON 对象 → schema 校验 → 引用白名单校验 → 将具体错误和非法输出交回模型 → 有界修复 → 最后确定性规范化或失败。

## 4. 真实 HTTP 全链路

### 4.1 场景

首问：“我在两条路之间犹豫，不知道该怎么选。”预期系统追问；第二轮补充北京互联网 offer 与家乡银行的权衡并要求直接给参照。预期 `ask → respond`，最多 2 条知乎 query，至少 1 个来源，最终状态 `WAITING_FOR_FOLLOW_UP`。

### 4.2 失败基线

- v1 使用当前默认严格 client，首轮 HTTP 502 后 runner 断言退出；旧 runner 没有落完整响应，只保留回溯记录。
- v2 换用平衡 JSON 提取，但保留旧 `LlmGateway`，只通过 3/15。首轮为 `LLM_INVALID_RESPONSE`，第二轮为 `ANSWER_INVALID`。随后以相同 turn 再发时意外成功，但这是失败后的新执行，不是成功结果的幂等重放，因此不能计为通过。
- v2 的旧 summary 把失败响应中的 query 数记成 0；审计事件显示两次 retrieve 各实际调用 2 条 query，额度变化也确认 v2 共消耗 4 次知乎调用。失败检索结果留在 session，说明当前编排缺少事务回滚/失败幂等保护。

根因是旧修复 prompt 没有携带上一版非法 JSON 和具体校验错误；答案引用合法性又到 AnswerBuilder 才验证，超过模型可修复边界。

### 4.3 v3 成功结果

v3 使用 `ResilientLlmClient` + `ValidatedLlmGateway`，在模型网关完成 JSON 提取、结构校验、来源白名单和最多两次带错误修复。

| 指标 | 结果 |
|---|---:|
| 验收项 | 16/16 |
| 动作 | ask → respond |
| 首轮延迟 | 1,273 ms |
| 第二轮完整回答延迟 | 13,111 ms |
| 知乎 query | 2 |
| 保存并回读来源 | 10 |
| 答案契约 | 通过 |
| 最终状态 | WAITING_FOR_FOLLOW_UP |
| 成功后同 turn 重放 | 返回完全相同结果 |
| session 用户消息数 | 2，未因重放增加 |

v3 消耗 2 次知乎调用。本轮全链路开始前余额为 4992；v2 消耗 4、v3 消耗 2，最后额度查询为总量 5000、已用 14、剩余 4986。额度查询本身不消耗业务额度。

## 5. 还不能声称什么

- 只有 4 个检索案例和 1 个真实全链路场景，不能估计生产可靠率。
- selector 对照标签并非独立双盲金标准，0.95 accuracy 只能用于开发期回归。
- 浏览器前端尚未接 API，加载动画和页面组件还没有被真实响应驱动。
- v3 runner 注入了新网关；默认 `createApp` 仍使用旧网关，若要成为正式产品路径，需要把新网关接入生产 composition 并补迁移测试。
- 失败检索的 session 原子性仍需修复，否则客户端重试会重复消耗知乎额度。

## 6. 建议的下一步顺序

1. 把 `ValidatedLlmGateway` 接到默认 `createApp`，并为失败 turn 加事务回滚或可恢复的 idempotency 记录。
2. 前端接入 session/message/source API，再按 `browser-acceptance.md` 实现 Playwright 主场景和异常场景。
3. 让第二位评审独立标注同一批 Top-5，报告 raw agreement 与 Cohen's kappa。
4. 扩充案例集后再比较模型和 query 策略，不用当前小样本结果做泛化宣传。
