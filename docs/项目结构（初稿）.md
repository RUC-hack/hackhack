# 项目结构

Kevin  
2026-09-04

## 一、总体目标

系统面向在重大选择中感到迷茫的大学生，通过多轮对话明确问题，再从知乎检索相关人生经验，抽取并聚合成可比较的选择路径。

系统输出的是“人生参照”，不是人生预测：

- 展示别人走过的路径；
- 对比路径的收益、代价、结果和遗憾；
- 保留知乎来源，允许用户回看原文；
- 不输出没有依据的成功率、概率或确定性结论。

## 二、核心处理流程

```text
用户输入困惑
  -> 会话初始化
  -> 问题识别与必要追问
  -> 用户画像 / 约束提取
  -> 检索计划生成
  -> 知乎经验检索
  -> 去重、排序与来源保留
  -> Experience Schema 抽取
  -> 人生路径聚类
  -> 收益 / 代价 / 代表案例生成
  -> 返回结构化结果与来源链接
```

只有在用户信息达到最低检索条件后才调用知乎，避免把每一轮闲聊都消耗成接口请求。知乎接口失败、超时、限额或返回结果不足时，切换到本地案例库继续完成演示。

## 三、后端架构

### 3.1 分层结构

```text
HTTP / SSE API
      |
Application Service
      |
Agent Orchestrator
  |       |        |
LLM   Retrieval   Answer Builder
          |
      DataProvider
       |       |
 ZhihuProvider  LocalDatasetProvider
          |
   Cache / Logs / Storage
```

后端只暴露稳定的业务接口。前端不能直接调用知乎或大模型，所有外部请求都从后端发出，便于凭证保护、限流、缓存和日志审计。

### 3.2 接口层

MVP 保持接口数量最少：

| 方法 | 路径 | 作用 |
|---|---|---|
| `GET` | `/api/health` | 检查服务是否可用以及当前 Provider 状态 |
| `POST` | `/api/sessions` | 创建一次人生选择分析会话 |
| `GET` | `/api/sessions/{session_id}` | 获取会话状态、画像和当前结果 |
| `POST` | `/api/sessions/{session_id}/messages` | 提交用户回答，推进追问或分析流程 |
| `GET` | `/api/sessions/{session_id}/events` | 可选：通过 SSE 流式返回阶段进度和最终结果 |
| `GET` | `/api/sources/{source_id}` | 获取已保存的来源摘要和原文链接 |

建议统一返回：

```json
{
  "ok": true,
  "data": {},
  "error": null,
  "request_id": "..."
}
```

错误至少区分：参数错误、会话不存在、LLM 失败、知乎接口失败、配额/频率限制和本地数据降级。

### 3.3 会话与 Agent 编排

不要在 MVP 中实现多个互相对话的 Agent。采用一个有明确阶段状态的 Orchestrator：

```text
COLLECTING_CONTEXT
  -> READY_FOR_RETRIEVAL
  -> RETRIEVING
  -> EXTRACTING_EXPERIENCES
  -> CLUSTERING_PATHS
  -> PRESENTING
  -> WAITING_FOR_REFLECTION
```

每一轮消息都先经过状态判断：

- 信息不足：只生成下一条必要追问；
- 信息足够：生成检索计划并调用 Provider；
- 检索结果不足：调整关键词或切换本地案例库；
- 结果足够：进入经验抽取和路径聚类；
- 用户要求修改方向：保留原案例，重新生成检索计划，不丢失会话记录。

### 3.4 用户画像与检索计划

画像只收集完成当前问题所需的最小信息，不做无关的人格标签收集：

```json
{
  "decision": "考研还是工作",
  "constraints": {
    "economic_pressure": "medium",
    "time_horizon": "3年",
    "family_expectation": "low"
  },
  "preferences": {
    "research_interest": "high",
    "uncertainty_tolerance": "medium"
  },
  "concerns": ["害怕选错", "担心错过机会"]
}
```

检索计划不直接把用户原话拼接成一个关键词，而是拆成多条路径查询，例如：

- 本科毕业直接工作；
- 读研后进入行业；
- 读研后转行；
- 放弃考研后重新选择。

### 3.5 知乎 Provider

定义统一接口，避免产品和知乎 API 强耦合：

```text
search(query, limit, filters) -> List[SourceDocument]
```

`SourceDocument` 至少包含：

```json
{
  "source_id": "zhihu:...",
  "title": "...",
  "author": "...",
  "summary": "...",
  "url": "https://...",
  "content_type": "answer",
  "retrieved_at": "...",
  "provider": "zhihu"
}
```

Provider 负责：

- 调用官方知乎搜索接口；
- 统一字段名称；
- 去除重复 URL；
- 保留原始摘要和来源链接；
- 做超时、有限重试和配额错误分类；
- 写入知乎调用日志；
- 将结果写入短期缓存，避免同一会话重复消耗额度。

不要在 Provider 中直接生成最终建议，也不要把知乎结果未经来源标记地混入普通知识库。

### 3.6 本地案例库 Provider

为了保证比赛现场可演示，至少实现：

```text
ZhihuProvider          # 在线知乎接口
LocalDatasetProvider   # 本地精选案例
MockProvider           # 开发和自动化测试
```

本地案例库可以先使用少量人工筛选的案例，字段与 `SourceDocument` 和 `ExperienceCase` 保持一致。切换 Provider 不应影响前端和 Agent 编排器。

### 3.7 Experience Schema

LLM 不直接返回长篇最终答案，而是先输出结构化经验：

```json
{
  "case_id": "...",
  "source_id": "zhihu:...",
  "background": {
    "age": 24,
    "education": "本科",
    "major": "计算机"
  },
  "decision": "读研还是工作",
  "chosen_path": "读研后转行",
  "motivation": ["想获得缓冲期"],
  "outcome": ["进入互联网行业"],
  "benefits": ["获得学历", "重新选择方向"],
  "costs": ["延迟收入", "方向错配风险"],
  "regrets": ["错过部分工作机会"],
  "time_horizon": "3年",
  "confidence": 0.72,
  "evidence_spans": ["...摘要中的依据..."]
}
```

字段缺失时必须保留 `null` 或空数组，不能让模型补造事实。`confidence` 只表示抽取可信度，不表示这个人生选择成功的概率。

### 3.8 路径聚类与答案构建

第一版不必引入复杂向量数据库，可以先采用：

1. LLM 按预定义路径标签分类；
2. 结合关键词和用户约束进行排序；
3. 对每条路径聚合重复的收益和代价；
4. 选择 1～3 个代表案例；
5. 为每个判断绑定 `source_id`。

最终结果建议包含：

```json
{
  "decision": "考研还是工作",
  "paths": [
    {
      "name": "直接工作",
      "benefits": [],
      "costs": [],
      "fit_for": [],
      "representative_cases": [],
      "reflection_questions": []
    }
  ],
  "disclaimer": "以下内容是相关人生经验的整理，不是结果预测。"
}
```

答案生成器只能使用已检索并保存的案例，不允许在最后一步凭空添加知乎不存在的观点或数据。

### 3.9 日志与存储

遵守 [项目结构性约束](./项目结构性约束.md)：

```text
logs/
├── conversations/
│   └── YYYY-MM-DD/session-<id>.jsonl
└── zhihu/
    └── YYYY-MM-DD/request-<id>.jsonl
```

日志记录：

- `request_id`、`session_id`、时间和阶段；
- 脱敏后的请求参数；
- Provider、查询词、结果数量和来源 ID；
- LLM 阶段输入输出摘要；
- 错误码、耗时和降级情况。

日志禁止记录：

- Access Secret、OAuth App Key、OAuth Token；
- authorization code；
- 用户不必要的身份证明或敏感个人信息；
- 未脱敏的完整凭证环境变量。

MVP 存储建议使用 SQLite 或 JSONL；只有出现多人并发、复杂查询或部署需求时再迁移 PostgreSQL。

## 五、项目约束

- 不把知乎当作统计学总体，不输出伪精确概率；
- 搜索摘要不是完整原文，始终保留来源 URL；
- 知乎接口失败时必须能切换本地数据；
- 不在前端暴露知乎或大模型凭证；
- 所有重大架构变更写入文档；
- 所有知乎调用和 Agent 对话写入 `logs/` 并脱敏；
- OAuth 不是检索知乎经验的必要条件，仅在确实需要用户用知乎登录时启用。

## 六、两天半实现优先级

1. 先打通单会话、单次追问、单次检索和结构化结果；
2. 接入 `LocalDatasetProvider`，保证离线演示；
3. 接入 `ZhihuProvider`，补充真实来源链接；
4. 完成路径对比卡片和来源查看；
5. 最后再做 SSE、缓存、向量检索和视觉优化。
