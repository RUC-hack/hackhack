# 项目结构

Kevin  
2026-09-04

## 一、总体目标

系统面向在重大选择中感到迷茫的大学生，通过多轮对话明确问题，再从知乎检索相关人生经验，帮助用户看见材料中的路径、主题、张力、转折和独特个案。

系统输出的是“人生参照”，不是人生预测：

- 展示别人走过的路径和无法被简单归类的经历；
- 根据材料对比收益、代价、结果、遗憾或其他真正出现的主题；
- 保留知乎来源，允许用户回看原文；
- 不输出没有依据的成功率、概率或确定性结论。

架构中的结构化数据只用于稳定传递来源、证据和状态，不预先规定人生经历必须包含哪些语义字段。原始材料必须先被完整保留，任何分类都只是针对当前问题的一次解释，不是对案例的永久定性。

## 二、核心处理流程

```text
用户输入困惑
  -> 会话初始化
  -> 问题识别与必要追问
  -> 用户画像 / 约束提取
  -> 检索计划生成
  -> 知乎经验检索
  -> 去重、排序与来源保留
  -> 原始证据包保存
  -> 开放式观察与主题提取
  -> 按当前问题发现路径 / 张力 / 时间线 / 独特个案
  -> 动态组织回答
  -> 返回可渲染内容与来源链接
```

只有在用户信息达到最低检索条件后才调用知乎，避免把每一轮闲聊都消耗成接口请求。知乎接口失败、超时、限额或返回结果不足时，切换到本地案例库继续完成演示。检索结果无法进入当前主题时不得丢弃，可以保留为独立个案、反例或“不确定材料”。

## 三、后端架构

### 3.1 分层结构

```text
HTTP / SSE API
      |
Application Service
      |
Agent Orchestrator
  |       |        |
LLM   Retrieval   Answer Builder
          |
      DataProvider
       |       |
 ZhihuProvider  LocalDatasetProvider
          |
   Cache / Logs / Storage
```

后端只暴露稳定的业务接口。前端不能直接调用知乎或大模型，所有外部请求都从后端发出，便于凭证保护、限流、缓存和日志审计。

### 3.2 接口层

MVP 保持接口数量最少：

| 方法 | 路径 | 作用 |
|---|---|---|
| `GET` | `/api/health` | 检查服务是否可用以及当前 Provider 状态 |
| `POST` | `/api/sessions` | 创建一次人生选择分析会话 |
| `GET` | `/api/sessions/{session_id}` | 获取会话状态、画像和当前结果 |
| `POST` | `/api/sessions/{session_id}/messages` | 提交用户回答，推进追问或分析流程 |
| `GET` | `/api/sessions/{session_id}/events` | 可选：通过 SSE 流式返回阶段进度和最终结果 |
| `GET` | `/api/sources/{source_id}` | 获取已保存的来源摘要和原文链接 |

建议统一返回：

```json
{
  "ok": true,
  "data": {},
  "error": null,
  "request_id": "..."
}
```

错误至少区分：参数错误、会话不存在、LLM 失败、知乎接口失败、配额/频率限制和本地数据降级。

### 3.3 会话与 Agent 编排

不要在 MVP 中实现多个互相对话的 Agent。采用一个有明确阶段状态的 Orchestrator。下面是可回退、可跳过的处理阶段，不要求每个请求严格走完同一条直线：

```text
COLLECTING_CONTEXT
  -> READY_FOR_RETRIEVAL
  -> RETRIEVING
  -> EXTRACTING_EXPERIENCES
  -> DISCOVERING_PATTERNS
  -> PRESENTING
  -> WAITING_FOR_REFLECTION
```

每一轮消息都先经过状态判断：

- 信息不足：只生成下一条必要追问；
- 信息足够：生成检索计划并调用 Provider；
- 检索结果不足：调整关键词或切换本地案例库；
- 结果足够：先保存证据，再开放式提取观察，随后选择适合当前材料的组织方式；
- 案例无法归类：保留原始材料并标记为独立个案、反例或不确定，不把它静默删除；
- 用户要求修改方向：保留原案例，重新生成检索计划，不丢失会话记录。

### 3.4 用户画像与检索计划

画像只收集完成当前问题所需的最小信息，不做无关的人格标签收集。除当前问题的自然语言描述外，其余上下文使用开放条目，不要求所有用户回答都落入同一组字段：

```json
{
  "problem_statement": "我不知道应该考研还是工作",
  "context_items": [
    {
      "label": "经济压力",
      "value": "希望尽快独立，但没有迫切负担",
      "source": "user",
      "certainty": "explicit"
    },
    {
      "label": "尚未说清的担忧",
      "value": "害怕过早锁定方向",
      "source": "assistant_inference",
      "certainty": "tentative"
    }
  ],
  "user_words": ["我其实不是不喜欢研究，只是不知道自己能不能坚持"]
}
```

`label` 由当前对话动态产生。模型推断和用户明确表达必须区分，暂时无法确认的内容不能被固化为用户画像事实。

检索计划不直接把用户原话拼接成一个关键词，也不要求先确定封闭的路径分类。可以根据冲突、场景、阶段、反例和用户用词生成多条查询，例如：

- 本科毕业直接工作；
- 读研后进入行业；
- 读研后转行；
- 放弃考研后重新选择。

### 3.5 知乎 Provider

定义统一接口，避免产品和知乎 API 强耦合：

```text
search(query, limit, filters) -> List[SourceDocument]
```

`SourceDocument` 至少包含：

```json
{
  "source_id": "zhihu:...",
  "title": "...",
  "author": "...",
  "summary": "...",
  "url": "https://...",
  "content_type": "answer",
  "retrieved_at": "...",
  "provider": "zhihu"
}
```

Provider 负责：

- 调用官方知乎搜索接口；
- 统一字段名称；
- 去除重复 URL；
- 保留原始摘要和来源链接；
- 做超时、有限重试和配额错误分类；
- 写入知乎调用日志；
- 将结果写入短期缓存，避免同一会话重复消耗额度。

不要在 Provider 中直接生成最终建议，也不要把知乎结果未经来源标记地混入普通知识库。

### 3.6 本地案例库 Provider

为了保证比赛现场可演示，至少实现：

```text
ZhihuProvider          # 在线知乎接口
LocalDatasetProvider   # 本地精选案例
MockProvider           # 开发和自动化测试
```

本地案例库可以先使用少量人工筛选的案例，原始来源字段与 `SourceDocument` 保持一致；开放式观察可保存为 `EvidencePacket`，也可以在运行时重新生成。切换 Provider 不应影响前端和 Agent 编排器。

### 3.7 证据包与开放式经验表示

后端仍需要稳定的数据契约，但只固定来源追踪和证据完整性，不固定人生经历的语义分类。处理顺序是：

1. 原样保存 `SourceDocument`；
2. 针对当前用户问题，从原文中提取有证据的观察；
3. 允许动态产生主题标签；
4. 保留矛盾、未知、无法归类和同时属于多个主题的内容；
5. 后续组织方式改变时，可以从原始证据重新解释，而不是依赖已经压扁的旧分类。

建议使用开放的 `EvidencePacket`：

```json
{
  "case_id": "...",
  "source_id": "zhihu:...",
  "raw_summary": "保留的原始摘要",
  "narrative": "不强行拆字段的经历概述",
  "observations": [
    {
      "label": "一次意外机会改变了原计划",
      "value": "作者原本准备读研，实习转正后选择工作",
      "evidence": "与原始摘要逐字对应的片段",
      "certainty": "explicit"
    }
  ],
  "tensions": ["兴趣与经济独立之间的拉扯"],
  "unknowns": ["没有说明三年后的感受"],
  "candidate_relations": [
    {
      "theme": "计划被偶然事件改变",
      "strength": "possible"
    }
  ]
}
```

这里的 `observations.label`、`tensions` 和 `candidate_relations.theme` 都是开放文本，可以随问题变化。除了 `case_id`、`source_id`、原始材料和证据引用之外，不要求每个案例拥有相同字段，也不要求每个案例只有一个分类。

如果模型没有足够证据，只能写入 `unknowns`，不能为了满足模板推断年龄、背景、动机、结果或遗憾。任何二次主题归纳都必须能回到 `source_id` 和具体 `evidence`。

### 3.8 动态归纳与答案构建

第一版不必引入复杂向量数据库，也不使用预定义路径标签强制分类。系统先查看实际检索到的材料，再选择组织方式：

- 存在清晰分支时，生成路径比较；
- 经历随时间变化明显时，生成时间线；
- 多数案例围绕相同矛盾时，生成主题或张力地图；
- 案例差异很大时，保留为案例拼图；
- 材料不足或互相冲突时，明确展示不确定性和冲突；
- 某个案例无法归类但对用户有启发时，作为独立个案呈现。

最终回答只固定渲染所需的外壳，不固定栏目数量和内容顺序：

```json
{
  "summary": "根据当前问题和材料生成的开场说明",
  "sections": [
    {
      "kind": "由后端建议的展示方式",
      "title": "根据当前材料生成的标题",
      "content": {},
      "source_ids": ["zhihu:..."]
    }
  ],
  "unclassified_case_ids": [],
  "limitations": ["以下内容是相关人生经验的整理，不是结果预测。"]
}
```

`sections` 可以有零个、一个或多个；`kind` 只是前端渲染建议，前端遇到未知类型时应降级显示为普通文本或案例卡片。系统不预设必须输出三条路径，也不要求每条回答都包含收益、代价、适合人群等固定栏目。

答案生成器只能使用已保存的证据包，不允许在最后一步凭空添加知乎不存在的观点或数据。测试应验证证据可追溯和材料保留，而不是断言模型必须输出某个固定标签或句式。

### 3.9 日志与存储

遵守 [项目结构性约束](./项目结构性约束.md)：

```text
logs/
├── conversations/
│   └── YYYY-MM-DD/session-<id>.jsonl
└── zhihu/
    └── YYYY-MM-DD/request-<id>.jsonl
```

日志记录：

- `request_id`、`session_id`、时间和阶段；
- 脱敏后的请求参数；
- Provider、查询词、结果数量和来源 ID；
- LLM 阶段输入输出摘要；
- 错误码、耗时和降级情况。

日志禁止记录：

- Access Secret、OAuth App Key、OAuth Token；
- authorization code；
- 用户不必要的身份证明或敏感个人信息；
- 未脱敏的完整凭证环境变量。

MVP 存储建议使用 SQLite 或 JSONL；只有出现多人并发、复杂查询或部署需求时再迁移 PostgreSQL。

## 五、测试与验收

### 5.1 测试原则

生成式系统不能依赖“期望回答和模型输出逐字相等”的测试。测试重点是稳定行为和质量不变量：

- 每条事实性归纳都能追溯到 `source_id` 和证据片段；
- 原始摘要不会被后续分类覆盖或丢失；
- 无法归类、互相矛盾和信息不足的案例仍被保留；
- 回答形式可以变化，但不能出现无来源的知乎观点；
- 相同输入允许措辞不同，但核心来源集合和限制说明应保持合理稳定；
- 所有日志和错误响应都不能泄露凭证或 Token。

### 5.2 单元测试

`tests/unit/` 覆盖纯函数和模块边界：

- `SourceDocument` 字段归一化；
- URL 和来源 ID 去重；
- 上下文条目的显式信息与模型推断标记；
- 证据片段与原始摘要的一致性检查；
- 无法归类案例的保留；
- 日志脱敏；
- Orchestrator 状态推进、回退和中止；
- 缓存键和过期策略。

### 5.3 契约测试

`tests/contract/` 验证前后端和 Provider 的稳定契约：

- API 成功与错误外壳；
- `ZhihuProvider`、`LocalDatasetProvider` 和 `MockProvider` 返回相同的最小来源字段；
- 未知 `section.kind` 能被前端降级显示；
- Provider 切换不会改变会话接口；
- 日志结构包含 `request_id`、`session_id`、阶段和来源 ID。

契约测试只约束技术字段，不约束模型必须输出固定的主题、路径数量或回答栏目。

### 5.4 集成测试

`tests/integration/` 使用 Mock Provider 和可控的模型响应完成端到端流程：

```text
创建会话
  -> 提交多样化用户回答
  -> 追问或直接检索
  -> 保存来源
  -> 生成开放式观察
  -> 组织回答
  -> 验证来源链接和日志
```

至少覆盖：常规选择题、叙述型困惑、用户中途改口、没有明确二选一、材料互相冲突、没有足够信息以及无法形成路径分类的案例。

### 5.5 质量回归测试

`tests/quality/` 使用一组固定但表达多样的匿名样例，检查规则和评分，而不是比较完整文案：

| 指标 | MVP 验收要求 |
|---|---|
| 来源可追溯率 | 所有引用知乎材料的段落都有来源 |
| 无依据断言 | 不允许出现 |
| 原始材料保留 | 所有入选和未分类案例均可回查 |
| 未分类案例召回 | 不因缺字段而静默丢弃 |
| 回答适配性 | 不同问题可以选择不同组织形式 |
| 限制说明 | 涉及人生判断时必须出现 |

质量用例应包含不同长度、口语化表达、矛盾回答、隐含担忧、非典型路径和不完整知乎摘要，避免测试集本身只适配“考研还是工作”这一种范式。

### 5.6 故障与安全测试

必须注入以下故障：

- 知乎超时、空结果、频率限制和额度耗尽；
- 重复结果、字段缺失和无法解析的响应；
- LLM 返回非法 JSON、遗漏来源或生成不存在的来源 ID；
- 本地案例库不存在或损坏；
- 知乎正文中包含试图操纵模型的指令；
- 日志内容包含看似 Access Secret、OAuth Token 或 authorization code 的字符串。

预期行为分别是有限重试、明确错误、切换本地 Provider、保留原始材料、拒绝伪造来源和完成脱敏。检索到的网页文字一律视为不可信数据，不能作为系统指令执行。

### 5.7 真实接口冒烟测试

CI 默认不调用真实知乎或大模型接口，避免消耗额度和引入不稳定因素。比赛前由开发者显式开启一次冒烟测试：

1. 使用后端环境变量注入凭证；
2. 执行一条最小知乎搜索；
3. 验证返回标题、摘要和 URL；
4. 检查日志中没有凭证；
5. 模拟断网，验证本地 Provider 接管。

真实接口测试不得把响应全文作为长期测试快照；只保存脱敏后的必要字段和人工确认结果。

## 六、项目约束

- 不把知乎当作统计学总体，不输出伪精确概率；
- 搜索摘要不是完整原文，始终保留来源 URL；
- 知乎接口失败时必须能切换本地数据；
- 不在前端暴露知乎或大模型凭证；
- 所有重大架构变更写入文档；
- 所有知乎调用和 Agent 对话写入 `logs/` 并脱敏；
- 结构化仅用于传递证据和状态，不得强迫所有人生经历进入封闭分类；
- OAuth 不是检索知乎经验的必要条件，仅在确实需要用户用知乎登录时启用。

## 七、两天半实现优先级

1. 先打通单会话、追问、检索、证据保存和动态回答；
2. 同步完成单元测试、Provider 契约和日志脱敏测试；
3. 接入 `LocalDatasetProvider`，保证离线演示；
4. 接入 `ZhihuProvider`，补充真实来源链接和故障降级测试；
5. 完成能够展示多种 section 的前端和来源查看；
6. 最后再做 SSE、缓存、向量检索和视觉优化。
