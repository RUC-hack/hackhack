# 候选材料渐进分析设计（历史方案与当前兼容字段）

> 当前产品交互已恢复为统一回答模式：后端仍可使用 `SourceSelection` 从检索结果中筛选引用范围，但不会先把候选条目返回给用户；筛选完成后在同一请求内生成最终回答，前端统一展示回答及其可回看的来源。本文保留渐进式方案的字段和契约说明，涉及“后台分析”的段落仅作为历史记录。

## 1. 目标

在用户完成必要的上下文补充后，系统内部仍拆成两个阶段，但对用户统一返回最终回答：

1. 检索知乎材料，并由模型从已检索材料中筛选最多三组候选经历；
2. 针对候选材料生成最终综合回答，并在同一个 HTTP 请求中返回。

这样前端不会出现候选材料先于回答单独出现的等待态；最终回答完成后，再展示其中引用的知乎来源。

候选材料是参照，不是结论；筛选理由只能来自已保存的来源摘要，不能凭空补写人物背景或结果。

## 2. 处理流程

```text
用户完成问询
  -> AgentDecision(action=retrieve)
  -> RetrievalService 检索并持久化 SourceDocument/EvidencePacket
  -> SourceSelection 选择最多 3 组、每组最多 3 篇来源
  -> 保存候选材料
  -> AnswerBuilder 只分析被选中的来源
  -> 保存 current_answer，返回 action=respond，状态变为 WAITING_FOR_FOLLOW_UP
```

`POST /api/sessions/:id/messages` 等待最终答案后返回。`GET /api/sessions/:id` 仍可用于刷新页面和回读已完成的 `current_answer`，不再承担后台分析轮询职责。

## 3. 会话状态和持久化字段

继续复用现有状态：

```text
RETRIEVING -> REVIEWING_EVIDENCE -> PRESENTING -> WAITING_FOR_FOLLOW_UP
                                      |
                                      +-> FAILED_RECOVERABLE
```

新增会话字段：

```json
{
  "source_selection": {
    "selection_id": "selection_...",
    "context_version": 1,
    "status": "ready",
    "groups": []
  },
  "analysis": {
    "analysis_id": "analysis_...",
    "status": "completed",
    "error": null
  }
}
```

`analysis.status` 取值为 `idle | running | completed | failed`。模型筛选失败时使用按检索顺序生成的降级候选组，并把 `source_selection.status` 标为 `fallback`；统一回答生成失败时，会话置为 `FAILED_RECOVERABLE`，已保存的检索和候选选择仍可回读并允许后续重试。

回答生成绑定当前会话的 `session_id` 和 `context_version`。生成时如果发生错误，会话进入可恢复失败态，不能覆盖新话题。

## 4. SourceSelection 契约

模型只返回来源 ID 和轻量分类信息，来源标题、作者、摘要、链接由后端从 `SourceStore` 补全：

```json
{
  "groups": [
    {
      "key": "doctoral_path",
      "title": "读博后的年龄与职业窗口",
      "description": "材料聚焦读博年限、年龄和后续就业选择。",
      "items": [
        {
          "source_id": "zhihu:answer:...",
          "reason": "明确讨论读博后的年龄压力和岗位窗口。"
        }
      ]
    }
  ]
}
```

约束：

- 最多 3 个 `groups`；
- 每组最多 3 个 `items`；
- 同一个 `source_id` 不得出现在多个组；
- 所有 `source_id` 必须属于本轮检索结果；
- `title`、`description`、`reason` 都有字符上限；
- 空材料只能返回空 groups，不得生成虚构来源。

后端补全后的 `source_selection.groups[].items[]` 包含 `source` 公共视图，至少有 `source_id`、`title`、`author`、`summary`、`url`、`content_type`、`retrieved_at` 和 `provider`。

## 5. HTTP 返回约定

来源筛选和最终回答完成后：

```json
{
  "action": "respond",
  "state": "WAITING_FOR_FOLLOW_UP",
  "source_selection": { "selection_id": "...", "groups": [] },
  "analysis": { "analysis_id": "...", "status": "completed" },
  "answer": { "summary": "...", "sections": [] },
  "retrieval": { "queries": [], "source_ids": [], "meta": {} }
}
```

统一回答模式下，正常返回的 `analysis.status` 为 `completed`，并同时带有 `current_answer`；如果生成失败，系统保存 `FAILED_RECOVERABLE` 和错误信息，前端展示可重试提示。

## 6. 模型调用和成本控制

- `decision` 只负责判断是否开始检索；
- `selection` 只负责从检索结果中选 ID 和分类，不生成长文本；
- `answer` 只接收被选中的最多 9 个来源，并在同一个请求内完成；
- 最终回答继续遵守最多 3 条路径、每条最多 3 个引用的约束；
- 三个阶段分别记录耗时、prompt token、completion token 和 total token，不记录密钥、完整 prompt 或模型内部思维过程。

候选筛选会增加一次轻量模型调用，因此它的收益主要是缩小最终回答输入范围并提高来源可解释性；统一回答模式不再把这次调用拆成用户可见的等待阶段。

## 7. 并发、幂等和失败处理

- `client_turn_id` 继续保证用户重复提交不会重复创建筛选和回答；
- 同一会话同一 `selection_id` 在当前请求内只生成一次回答；
- 回答生成使用当前 HTTP 请求的 `AbortSignal`，超时或取消后进入可恢复失败态；
- 新话题或新上下文版本出现时，旧分析结果不得写回当前会话；
- 进程重启导致的 `running` 任务需要在恢复机制接入前标记为可重试状态；
- 候选材料和最终答案都通过审计日志记录阶段、状态、来源 ID 和安全 token 指标。

## 8. 验收标准

1. 自动化测试覆盖 SourceSelection 的字段、来源闭集、三组上限、每组两来源上限和重复来源拒绝；
2. Mock HTTP 流程直接返回 `respond`，会话为 `WAITING_FOR_FOLLOW_UP` 并拥有最终答案；
3. 答案生成失败时，会话进入 `FAILED_RECOVERABLE`，已保存的检索和候选选择仍可通过 `GET /api/sessions/:id` 获取；
4. 新上下文版本不会被旧后台任务覆盖；
5. 真实链路日志能区分 `decision`、`selection`、`answer` 三类模型调用。
