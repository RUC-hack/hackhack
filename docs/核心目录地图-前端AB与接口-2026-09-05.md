# HackHack 核心目录地图：前端 A、前端 B 与接口链路

> 依据完成 A → B 迁移后的当前工作区梳理。本文只描述核心运行逻辑，不展开实验、文档和测试文件。

## 先看全局

```text
hackhack/
├─ src/
│  ├─ prototypes/frontend-a/# 前端 A：完整静态原型归档，不接业务后端
│  ├─ index.html            # 前端 B：当前主展示页
│  ├─ app.js
│  ├─ styles.css
│  ├─ qa.html               # 前端 B：当前实际问答入口
│  ├─ qa.js                 # curated/live 协调与真实 API 链路
│  ├─ qa.css
│  ├─ journey.css           # 从 A 提炼的正式路径/人物组件
│  ├─ demo/curated-data.js  # 独立的精选演示数据
│  ├─ assets/               # B 使用的图片、人物 SVG
│  └─ server/               # 后端：会话、DeepSeek、知乎、证据、回答
├─ data/experiences.jsonl   # 知乎不可用时的本地降级数据
├─ scripts/                 # 启动前后端与环境检查
└─ experiments/             # 验证代码，不是产品运行入口
```

## 1. 前端 A：`src/prototypes/frontend-a/`

### 它是什么

A 是一套完整的静态产品演示：页面漂亮、流程完整，但“理解问题、匹配人物、生成路径”全部由浏览器里的固定数据和关键词规则模拟，没有连接项目后端。

```text
prototypes/frontend-a/index.html
  → question.html
  → matching.html
  → paths.html
```

### 核心文件

| 文件 | 当前职责 |
|---|---|
| `prototypes/frontend-a/index.html` | A 的展示首页 |
| `prototypes/frontend-a/app.js` | 首页内容渲染、导航、动画、Unsplash 图片 |
| `prototypes/frontend-a/styles.css` | A 的首页视觉系统 |
| `prototypes/frontend-a/question.html` | 用户输入人生问题 |
| `prototypes/frontend-a/matching.html` | “正在分析/匹配人群”的过渡动画 |
| `prototypes/frontend-a/paths.html` | 路径、人物卡片、人物详情、向人群提问 |
| `prototypes/frontend-a/journey.js` | A 的全部页面流程和本地交互逻辑 |
| `prototypes/frontend-a/journey-data.js` | career/migration/generic 三组虚构演示路径与人物数据 |
| `prototypes/frontend-a/journey.css` | 问题页、匹配页、路径页、人物池的核心视觉样式 |
| `prototypes/frontend-a/logo-mark.svg` | A 的 Logo 图形 |

### A 实际怎样工作

```text
用户输入问题
→ journey.js 保存到 sessionStorage
→ analyzeQuestion() 用关键词判断 career/migration/generic
→ matching.html 用定时器播放“分析”动画
→ journey-data.js 提供固定路径与人物
→ paths.html 渲染结果
→ 收藏写入 localStorage
```

A 中真正访问的网络接口只有可选的 Unsplash 图片接口；它不调用 `/api/sessions`，也不调用 DeepSeek 或知乎。

### A 中适合迁移给 B 的部分

- `journey.css` 的问题输入、匹配动画、路径列表、人物池和详情布局；
- `matching.html` 的阶段式等待体验；
- `paths.html` 的路径—人物—详情信息结构；
- `journey.js` 中纯 UI 函数的交互思路，如路径切换、人物切换、收藏和滚动；
- `logo-mark.svg` 与视觉语言。

### A 中不应迁移的部分

- `analyzeQuestion()` 的关键词假匹配；
- `journey-data.js` 的固定人物和固定结论；
- 用定时器假装后端已经完成检索；
- `publishCrowdPost()` 等没有真实服务支撑的业务动作；
- 依赖 `sessionStorage` 在多个 HTML 页面之间传递核心业务状态的做法。

## 2. 前端 B：`src/` 根目录

### 它是什么

B 是当前由 `npm start` 实际提供的前端。它包含展示首页和真正连接后端的问答页，并已经部分吸收 A 的视觉组件。

### 核心文件

| 文件 | 当前职责 |
|---|---|
| `src/index.html` | B 的主展示页，入口链接到 `qa.html` |
| `src/app.js` | 主展示页内容、导航、动画和图片 |
| `src/styles.css` | B 的全局视觉基础 |
| `src/qa.html` | B 的问题输入、对话区、路径结果和人物详情结构 |
| `src/qa.js` | B 的核心前端控制器：模式分流、API 请求、消息、答案、路径和来源渲染 |
| `src/qa.css` | B 对问答页的补充样式 |
| `src/journey.css` | 从 A 提炼出的正式路径、人物和详情组件样式 |
| `src/demo/curated-data.js` | 独立的精选演示答案与来源，不参与 live 请求 |
| `src/assets/people/figures.svg` | B 的人物插画集合 |

`qa.html` 现在直接引用正式样式：

```text
src/journey.css
```

因此 B 已不再运行时依赖 A 的归档目录。

### B 的两种运行模式

#### Curated 模式

```text
用户输入
→ qa.js 的 shouldUseCuratedFlow()
→ 命中毕业/就业/读博等关键词
→ 使用 demo/curated-data.js 中的 DEMO_SOURCES 和 DEMO_ANSWER
→ 播放本地动画并展示固定结果
```

这个模式不调用后端，适合稳定演示，但不是完整真实链路。

强制使用：

```text
qa.html?mode=curated
```

#### Live 模式

```text
用户输入
→ POST /api/sessions
→ POST /api/sessions/{id}/messages
→ 后端返回 ask / respond
→ qa.js 渲染追问或答案
→ GET /api/sources/{id}
→ 展示真实知乎来源
```

强制使用：

```text
qa.html?mode=live
```

### B 中最重要的函数区域

| `qa.js` 逻辑 | 职责 |
|---|---|
| `shouldUseCuratedFlow()` | 选择 curated 或 live |
| `request()` | 统一请求后端 API |
| `startSession()` | 创建一次用户会话 |
| `sendTurn()` | 发送一轮消息和 `client_turn_id` |
| `renderTurn()` | 处理 ask/respond/safety 等动作 |
| `startSearchRitual()` | 展示理解/检索阶段动画 |
| `appendAnswer()` | 渲染普通答案结构 |
| `buildMatchedPaths()` | 把后端 AnswerEnvelope 转成前端路径 |
| `renderMatchedPaths()` | 渲染路径和人物池 |
| `getSource()` / `renderSourceDetail()` | 读取并展示知乎来源 |

## 3. DeepSeek API 调用链

### 核心文件

| 文件 | 当前职责 |
|---|---|
| `src/server/integrations/resilient-llm-client.mjs` | 向 DeepSeek 发送 HTTP 请求，并从模型文本中提取合法 JSON |
| `src/server/services/validated-llm-gateway.mjs` | 校验模型决策/答案；把具体错误交回模型做有界修复 |
| `src/server/services/prompts.mjs` | 构造“下一步动作”和“基于证据回答”的提示词 |
| `src/server/services/answer-builder.mjs` | 把证据包交给模型，并检查答案引用 |
| `src/server/services/agent-orchestrator.mjs` | 决定什么时候调用模型判断、检索和生成答案 |
| `src/server/app.mjs` | 创建并连接上述组件 |

### 当前生产调用

当前 `src/server/app.mjs` 已经默认使用：

```text
ResilientLlmClient
→ ValidatedLlmGateway
```

不是旧的 `LlmClient + LlmGateway`。

### 两次主要模型调用

```text
第一次：decideNextAction()
用户信息 → DeepSeek → ask/retrieve/respond

第二次：buildGroundedAnswer()
知乎证据 → DeepSeek → AnswerEnvelope
```

模型不能直接控制数据库或调用知乎；它只返回受 contract 约束的 JSON。

## 4. 知乎接口调用链

### 核心文件

| 文件 | 当前职责 |
|---|---|
| `src/server/integrations/zhihu-search-client.mjs` | 发送知乎搜索 HTTP 请求，处理 Code、schema、超时、重试和限流 |
| `src/server/providers/zhihu-provider.mjs` | 将知乎 Items 清洗、去重、缓存并转成统一 SourceDocument |
| `src/server/services/retrieval-service.mjs` | 执行多 query 检索，并在失败/空结果时选择降级 |
| `src/server/providers/local-dataset-provider.mjs` | 使用本地案例作为降级来源 |
| `data/experiences.jsonl` | 本地降级案例数据 |
| `src/server/storage/source-store.mjs` | 保存来源，供前端按 source_id 回读 |

### 调用流程

```text
DeepSeek 返回 retrieve + queries
→ AgentOrchestrator
→ RetrievalService.searchMany()
→ ZhihuProvider.search()
→ ZhihuSearchClient 请求知乎 API
→ 标准化为 SourceDocument
→ SourceStore 保存
→ EvidenceService 生成证据包
→ DeepSeek 生成带 source_id 的答案
```

知乎不可用时：

```text
ZhihuProvider 失败或无结果
→ RetrievalService
→ LocalDatasetProvider
→ 回答中标记 degraded/本地降级限制
```

## 5. 后端总装配点

`src/server/app.mjs` 是整个项目最重要的组装文件：

```text
读取 runtime config
→ 创建 session/source store
→ 创建 Zhihu/Local/Mock Provider
→ 创建 RetrievalService
→ 创建 DeepSeek client 和 gateway
→ 创建 Session/Evidence/Answer 服务
→ 创建 AgentOrchestrator
→ 暴露 HTTP API
```

主要 API：

```text
GET  /api/health
POST /api/sessions
GET  /api/sessions/{id}
POST /api/sessions/{id}/messages
GET  /api/sources/{id}
```

## 6. 启动链路

```text
npm start
→ scripts/start-all.mjs
   ├─ src/server/main.mjs          # 后端 3000
   └─ scripts/frontend-server.mjs # 前端 8080，根目录为 src/
```

这意味着：

- B 的首页是 `http://localhost:8080/`；
- B 的问答页是 `http://localhost:8080/qa.html`；
- A 仍可通过 `/prototypes/frontend-a/...` 访问，但不是默认入口；
- `frontend-server.mjs` 生成 `/app-config.js`，把后端地址交给 B。

## 7. 当前代码混乱的核心位置

```text
1. A 和 B 仍各有 index.html / app.js / styles.css，但 A 已放入明确的 prototypes 归档边界。
2. B 的 qa.js 仍同时承担 API、状态、动画、路径转换和来源渲染，后续可继续按模块拆分。
3. curated 和 live 共用渲染器，但数据文件、模式标识和 source_id 前缀已经分离。
4. experiments 中有多代 run.mjs，但它们不属于产品运行链。
```

## 8. A 优化 B 的正确迁移方向

```text
前端 A 提供：视觉、过渡、布局、人物交互
前端 B 保留：API、session、真实状态、source_id、错误处理
后端提供：DeepSeek 决策、知乎检索、证据和最终回答
```

当前落地结果：

```text
A 的 journey.css / 匹配动画 / 路径与人物布局
                  ↓
B 的 qa.html / qa.css / 渲染函数

A 的静态数据与关键词假匹配
                  ✕ 不迁移

B 的 API 和真实结果
                  ✓ 保留为唯一业务真相
```

一句话概括：A 是视觉原型库，B 才是产品前端；应该把 A 的表现层拆给 B，而不是把 A 的模拟业务流程整体接进来。
