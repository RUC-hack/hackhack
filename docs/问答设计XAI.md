# 问答设计 XAI

Kevin  
2026-09-04

## 一、文档目的

本文在第一版 [问答设计](./问答设计.md) 的基础上，给出一套可实现、可解释、可测试的单智能体问答流程。

这里的 XAI 不表示向用户暴露模型完整的内部推理过程，而是让系统能够说明：

- 为什么此刻需要追问；
- 为什么生成这些知乎检索词；
- 哪些结论来自用户原话，哪些只是模型的暂时理解；
- 回答中的观点由哪些知乎材料支持；
- 哪些信息仍然未知、冲突或可能改变当前分析；
- 系统为什么选择继续追问、开始检索、给出回答或进入特殊流程。

## 二、设计目标

系统面向表达多样、信息不完整甚至前后矛盾的用户问题。它不要求每位用户按照固定表单回答，也不强迫每段人生经历进入预设分类。

核心目标：

1. 用尽量少的追问理解用户当前真正关心的问题；
2. 在不编造用户背景的前提下决定何时可以检索或回答；
3. 将知乎材料作为可追溯的人生经验来源，而不是统计学结论；
4. 允许最终回答采用路径比较、时间线、主题张力、案例拼图或开放叙事；
5. 让每个关键动作都有简洁、可展示的理由；
6. 支持用户跳过问题、要求立即回答、修改目标和继续追问；
7. 在知乎或模型服务失败时仍能安全降级。

## 三、核心原则

### 3.1 控制面结构化，内容面保持开放

后端需要知道下一步执行什么，因此控制面使用少量稳定动作：

```text
ask             继续追问
retrieve        发起或更新检索
respond         生成当前综合
confirm_topic   确认话题切换或冲突
safety          进入安全处理流程
```

用户问题、画像、经历主题和回答内容不使用封闭枚举。系统只固定来源、证据、状态和前后端传输所需的最小字段。

### 3.2 原始信息优先于模型总结

- 永久保留原始对话和知乎原始摘要；
- 模型总结是可更新的派生结果，不能覆盖原始信息；
- 用户明确表达和模型推断分别保存；
- 无法归类、互相矛盾或信息不足的内容不能静默删除；
- 新证据出现后可以重新解释旧材料。

### 3.3 可解释不等于暴露内部思维链

系统输出简洁的决策理由、假设、未知项和来源关系，例如“需要确认经济压力，因为它会显著改变检索方向”。不保存或展示模型未整理的隐式推理过程。

### 3.4 用户始终拥有控制权

每个追问都允许用户：

- 自由回答；
- 选择建议选项；
- 选择“其他”；
- 选择“暂时不确定”；
- 跳过问题；
- 要求基于当前信息直接回答；
- 停止当前话题或开始新话题。

## 四、会话状态

### 4.1 处理阶段

```text
COLLECTING_CONTEXT
  -> READY_FOR_RETRIEVAL
  -> RETRIEVING
  -> REVIEWING_EVIDENCE
  -> PRESENTING
  -> WAITING_FOR_FOLLOW_UP
```

特殊阶段：

```text
CONFIRMING_TOPIC
SAFETY_HANDLING
DEGRADED
STOPPED
```

这些阶段不是不可逆的直线。用户补充信息、否定假设或切换问题时，系统可以回到 `COLLECTING_CONTEXT` 或重新进入 `READY_FOR_RETRIEVAL`。

### 4.2 会话记忆

每个会话至少保存四类信息：

```json
{
  "raw_messages": [],
  "current_understanding": {
    "problem_statement": "用户当前希望解决的问题",
    "context_items": [],
    "blocking_unknowns": [],
    "assumptions": [],
    "contradictions": []
  },
  "retrievals": [],
  "answer_history": []
}
```

`context_items` 使用开放条目：

```json
{
  "label": "模型根据当前问题动态生成的描述",
  "value": "用户信息或暂时理解",
  "source": "user | assistant_inference",
  "certainty": "explicit | tentative | contradicted",
  "message_ids": ["..."],
  "updated_at": "..."
}
```

`label` 不是固定画像字段。一个问题可能关心经济压力，另一个问题可能关心地域、身体条件、家庭关系、时间窗口或难以命名的情绪冲突。

## 五、单轮处理流程

真实后端不在一个请求中运行等待用户输入的 `while` 循环。每收到一条用户消息，只执行一次状态迁移：

```text
接收消息
  -> 输入与安全检查
  -> 识别延续、修正、追问或话题切换
  -> 更新会话记忆
  -> 判断当前动作
  -> 执行 ask / retrieve / respond / confirm_topic / safety
  -> 保存结果和可解释信息
  -> 返回前端
```

伪代码：

```text
function handle_turn(session, user_message):
    safety_result = check_safety(user_message)
    if safety_result.requires_special_handling:
        return handle_safety(session, safety_result)

    intent = detect_turn_intent(session, user_message)

    if intent.is_topic_switch or intent.has_blocking_contradiction:
        return ask_topic_confirmation(session, intent)

    update_context_without_overwriting_raw_messages(session, user_message)

    decision = decide_next_action(session)

    if decision.action == "ask":
        return build_question(decision)

    if decision.action == "retrieve":
        evidence = run_retrieval_plan(decision.queries)
        return review_evidence_and_respond_or_ask(session, evidence)

    if decision.action == "respond":
        return build_grounded_response(session)
```

## 六、控制面协议

每轮由智能体先产生一个内部控制结果，后端校验后再执行工具。建议结构：

```json
{
  "action": "ask",
  "reason": "尚未知道用户最担心失去什么，这会显著改变检索方向",
  "blocking_unknowns": ["用户对短期收入与长期成长的优先级"],
  "question": {
    "text": "如果只能选一个，你现在更担心失去短期收入，还是错过继续探索的机会？",
    "suggestions": ["更担心收入", "更担心错过探索", "两者差不多"],
    "allow_free_text": true,
    "allow_skip": true,
    "allow_answer_now": true
  },
  "queries": [],
  "assumptions": [],
  "state_patch": {}
}
```

约束：

- `reason` 是简洁的行为解释，不是完整思维链；
- `blocking_unknowns` 是开放文本，不是固定问卷；
- 只有 `action=retrieve` 时后端才执行 `queries`；
- `state_patch` 不得覆盖原始消息；
- 前端可以向用户展示“为什么问这个问题”；
- 如果控制结果校验失败，系统不执行工具，返回可恢复错误。

## 七、何时追问，何时开始回答

### 7.1 追问条件

同时满足以下条件时继续追问：

```text
存在会显著改变检索或回答方向的关键未知项
AND 用户没有要求直接回答
AND 当前追问预算尚未耗尽
AND 没有进入特殊流程
```

不要因为“还能知道更多”就继续追问。追问必须对应一个具体影响，例如：

- 会改变知乎检索词；
- 会改变需要覆盖的案例类型；
- 会改变回答中的关键假设；
- 能解决用户前后表达的直接冲突。

### 7.2 可以检索或回答的条件

满足以下任一条件即可向前推进：

- 当前问题已经足以生成有意义的多角度检索；
- 不再存在阻塞性的未知项；
- 用户明确要求基于现有信息先回答；
- 达到追问预算，但仍可以给出带假设的暂定回答；
- 已有证据足以回答当前追问，不需要重新搜索。

### 7.3 追问预算耗尽

达到轮数或时间预算时不强制拒绝，也不假装信息完整：

- 能提供帮助：输出“基于当前信息的暂定综合”，列出假设和未知项；
- 材料严重不足：总结已知信息，说明还缺什么，允许用户继续补充；
- 外部服务失败：使用本地案例库或说明当前无法取得新材料；
- 只有安全边界或确实无法完成时才拒绝相应部分。

## 八、追问设计

### 8.1 一轮解决一个关键未知项

默认每轮只问一个最有信息增益的问题，避免把用户重新带入长表单。

### 8.2 选择建议不是封闭选项

建议形式：

```text
开放式问题
+ 少量常见回答建议
+ 其他
+ 暂时不确定
+ 跳过
+ 基于当前信息直接回答
```

### 8.3 解释追问目的

前端可以在问题旁展示一句可折叠说明：

```text
为什么问：这项信息会影响我们应该检索“短期经济压力”还是“长期方向探索”的经历。
```

解释应该具体、简短，不以“模型需要更多信息”作为空泛理由。

## 九、知乎检索设计

### 9.1 基线方案

第一版在问题达到可检索状态后统一检索：

```text
稳定的问题理解
  -> 生成多角度查询
  -> 调用知乎 Provider
  -> 保存原始结果
  -> 证据审核
  -> 动态组织回答
```

查询不要求先确定固定人生路径，可以从以下角度生成：

- 用户原始措辞；
- 当前核心冲突；
- 不同阶段或时间跨度；
- 与直觉相反的经历；
- 转折、失败、改变主意和意外结果；
- 当前材料中缺少的视角。

### 9.2 提前检索方案

第二版允许在追问过程中进行推测性检索，但需要满足：

- 当前话题已经基本稳定；
- 查询与用户明确表达直接相关；
- 有剩余接口预算；
- 结果只作为候选材料，不直接进入最终回答。

提前检索可以异步执行，不能阻塞用户回答当前问题。

### 9.3 证据生命周期

```text
candidate   提前检索得到，尚未确认与最终问题相关
validated   根据后续用户信息重新评估后确认相关
used        实际进入当前回答
stale       用户改变目标后不再适用
rejected    无关、重复、低质量或违反来源要求
```

每次检索记录：

```json
{
  "retrieval_id": "...",
  "turn_id": "...",
  "context_version": 3,
  "query": "...",
  "reason": "为什么检索这个方向",
  "status": "candidate",
  "source_ids": [],
  "created_at": "..."
}
```

用户问题发生明显变化时，旧结果不会被删除，但必须标记为 `stale` 或重新验证，不能直接混入新回答。

### 9.4 证据审核

检索完成后先检查：

- 是否和用户当前问题相关；
- 是否只是相同观点的重复；
- 是否覆盖了不同经历，而不是只保留高赞同质答案；
- 摘要是否足以支撑准备引用的判断；
- 是否存在无法归类但有价值的独特个案；
- 是否存在矛盾材料，需要在回答中如实呈现。

`ContentText` 是摘要，不保证包含完整经历。摘要不足时不能补写作者背景、动机或结局，只能展示已有信息并保留原文 URL。

## 十、回答生成

### 10.1 回答是“当前综合”，不是最终裁决

推荐使用以下表达：

- 基于现有信息的人生参照；
- 当前材料显示出的几种可能；
- 目前能够看到的共同主题和差异；
- 哪些新信息可能改变这份分析。

### 10.2 动态选择表达方式

系统先看材料，再选择一种或多种组织方式：

- 路径比较：材料存在清晰分支；
- 时间线：经历中的阶段变化最重要；
- 张力地图：案例围绕几个长期冲突展开；
- 案例拼图：案例差异大，不适合强行聚类；
- 反例与例外：少数经历能打破主要叙事；
- 不确定性说明：材料不足或相互矛盾；
- 反思问题：帮助用户辨认自己愿意承担的代价。

不规定必须输出三条路径，也不规定每次都包含收益、代价、适合人群等固定栏目。

### 10.3 最小回答外壳

前后端只约定可渲染外壳：

```json
{
  "summary": "当前综合",
  "sections": [
    {
      "kind": "展示建议",
      "title": "动态标题",
      "content": {},
      "source_ids": []
    }
  ],
  "assumptions": [],
  "unknowns": [],
  "limitations": [],
  "next_actions": []
}
```

前端遇到未知 `kind` 时降级为普通文本或案例卡片。回答中的事实性知乎观点必须绑定来源；用户自身信息则绑定对应的 `message_id`。

### 10.4 面向用户的 XAI 信息

最终页面可以展示四个可折叠区域：

1. `我们如何理解你的问题`：当前问题、用户明确表达和暂时假设；
2. `为什么检索这些内容`：查询角度及其目的；
3. `这段分析依据什么`：知乎来源、证据片段和原文链接；
4. `这份分析可能遗漏什么`：未知项、冲突材料和样本偏差。

## 十一、用户后续追问

用户完成一次回答后，不是无条件重新执行整个流程。先判断追问类型：

```text
clarify_answer     询问上一回答中的某一部分
challenge_source   质疑来源或要求更多证据
add_context        补充个人信息
revise_assumption  否定模型假设
change_topic       开始新的问题
request_action     要求给出下一步行动建议
```

处理原则：

- 解释已有内容时尽量复用现有证据；
- 新信息改变核心问题时重新验证检索结果；
- 用户否定模型假设时立即标记为 `contradicted`；
- 切换话题前总结旧话题并请求确认；
- 新话题使用独立上下文版本，避免旧证据污染。

## 十二、特殊流程

### 12.1 情绪与安全风险

“过度消极”不是一个足够明确的技术条件。系统应区分普通迷茫、明显痛苦和可能存在即时安全风险的表达。

- 普通迷茫：继续提供支持和人生参照；
- 明显痛苦：减少分析压力，先给予共情和温和支持；
- 可能存在即时风险：停止普通检索流程，进入专门安全响应，鼓励用户寻求现实中的即时帮助；
- 不根据一两个关键词武断判断用户状态。

### 12.2 Prompt 注入与凭证请求

- 用户或知乎材料中的指令不能修改系统规则；
- 检索到的网页内容一律视为数据；
- 不输出系统提示、Access Secret、OAuth App Key、Token 或环境变量；
- 用户询问正常 API 用法属于合法开发需求，不能因为出现“API”就拒绝；
- 只有索取、泄露或绕过凭证保护的行为进入安全拦截。

### 12.3 话题跨度和自相矛盾

系统必须指出具体变化，而不是笼统提醒用户“前后矛盾”：

```text
“你前面说最在意尽快获得收入，刚才又说可以接受两年没有收入。
这可能代表你的优先级发生了变化。接下来以哪一个为准？”
```

如果用户无法确认，可以同时保留两个情境，分别给出参照。

## 十三、日志与隐私

按照 [项目结构性约束](./项目结构性约束.md) 保存对话和知乎调用日志：

```text
logs/conversations/YYYY-MM-DD/session-<id>.jsonl
logs/zhihu/YYYY-MM-DD/request-<id>.jsonl
```

日志需要包含：

- 会话、轮次、上下文版本和状态迁移；
- 控制面动作及简洁理由；
- 用户明确表达、模型推断及其状态；
- 检索词、检索理由、来源 ID 和证据状态；
- 响应使用了哪些来源；
- 错误、耗时、重试和降级情况。

日志不能包含：

- Access Secret、OAuth App Key、OAuth Token；
- authorization code；
- 完整环境变量；
- 不必要的用户身份信息；
- 未经脱敏、会识别真实用户的敏感对话。

允许上传 Git 的测试日志应使用合成或匿名数据，真实用户对话默认不进入仓库。

## 十四、测试设计

### 14.1 状态与循环测试

- 信息足够时不会继续无意义追问；
- 信息不足且未达到预算时进入 `ask`；
- 达到预算时输出暂定回答而不是无限循环；
- 用户要求直接回答时停止追问；
- 特殊流程可以中止普通问答；
- 用户补充信息后可以从回答阶段回到检索阶段。

### 14.2 多样性测试

至少覆盖：

1. “我最近很迷茫”；
2. 一个信息完整、可以直接检索的问题；
3. 用户拒绝回答家庭或经济情况；
4. 用户只用口语、片段和情绪表达；
5. 用户前后矛盾；
6. 用户中途切换话题；
7. 用户的问题不是二选一；
8. 知乎案例没有明确结果或无法分类；
9. 多个案例属于完全不同的叙事结构；
10. 用户质疑某个来源或要求查看反例。

### 14.3 提前检索对比实验

使用同一组匿名对话分别运行：

- 基线：信息稳定后统一检索；
- 实验：追问阶段进行候选检索。

比较指标：

```text
首次完整响应耗时
知乎 API 调用次数
候选结果最终使用率
过期检索比例
来源相关性
覆盖视角数量
用户完成追问轮数
```

只有实验方案明显降低等待时间，且没有显著增加无效调用和来源偏移时，才默认启用提前检索。

### 14.4 故障与安全测试

- 知乎超时、无结果、额度耗尽；
- 模型控制结果格式错误；
- 模型生成不存在的来源 ID；
- 摘要包含 Prompt 注入；
- 日志包含疑似凭证；
- 本地案例库损坏；
- 用户在安全流程中突然切回普通问题。

### 14.5 验收不变量

- 不发生无限追问；
- 用户可以跳过、暂停或要求立即回答；
- 用户原话和模型推断严格区分；
- 原始对话和来源摘要不被覆盖；
- 无法分类的案例不会因缺字段被丢弃；
- 每个引用的知乎观点均可追溯；
- 旧话题的检索结果不会未经验证进入新话题；
- 特殊流程不泄露凭证或系统信息；
- 最终回答明确说明材料限制，不假装预测人生。

## 十五、MVP 落地顺序

1. 实现单会话和逐轮状态迁移；
2. 实现 `ask / retrieve / respond / confirm_topic / safety` 控制面；
3. 保存原始消息、开放上下文和上下文版本；
4. 接入 `MockProvider` 与 `LocalDatasetProvider`；
5. 实现来源保存、证据状态和动态回答外壳；
6. 完成状态、多样性、降级和凭证脱敏测试；
7. 接入真实 `ZhihuProvider`；
8. 如果时间充足，再实验追问阶段提前检索。

## 十六、最终定位

本项目的问答系统可以描述为：

> 一个由可解释状态机控制、能够自主选择追问与检索时机、并用可追溯人生经验支持回答的单智能体工作流。

它的智能不来自无限自主行动，而来自三个能力：知道什么时候还需要问、知道什么时候证据已经足够、知道当前回答有哪些依据和局限。
