# 知乎人生经验检索闭环实验

## 目标

验证下面这条链路是否足以支撑黑客松 MVP：

```text
用户困境
  -> 提示词生成多个检索 query
  -> 知乎站内搜索 API
  -> 去重和筛选
  -> 基于检索证据生成带来源的人生参照回答
```

本实验不把“HTTP 请求成功”当作产品可行。它分别检验接口可靠性、资料可用性、Query Builder 质量、回答忠实度和人生路径覆盖度。

## 已知接口边界

仓库内资料给出的站内搜索接口为：

```text
GET https://developer.zhihu.com/api/v1/content/zhihu_search
```

一次请求最多返回 10 条。核心字段是 `Title`、`ContentText`、`Url`、`VoteUpCount`、`AuthorName`、`AuthorityLevel` 和 `RankingScore`。

`ContentText` 是搜索摘要，不保证包含完整回答。因此“摘要是否足以支持人生经验抽取”必须作为独立判定门，不能默认成立。

## 三阶段实验

### A 人工 Query 上限测试

先用人工设计的高质量 query 测试知乎接口本身。每个案例覆盖选择的两端、后悔或代价、转向或退出等角度。

如果人工 query 都拿不到足够真实经历，就不再优化模型提示词；问题位于接口覆盖、索引质量或摘要长度。

### B Query Builder 对照实验

对每个案例比较三种策略：

| 组别 | Query 来源 | 用途 |
|---|---|---|
| B0 | 直接使用用户原话 | 最简单基线 |
| B1 | 普通提示词生成 1 条 query | 检验普通改写是否有效 |
| B2 | 结构化提示词生成 4 条互补 query | 检验检索计划 |
| Oracle | 人工设计的 4 条 query | 参考上限 |

固定模型、版本、temperature 和提示词版本。先保存模型生成的 query，再执行搜索，避免把模型随机性和搜索波动混在一起。

### C 固定证据下的回答测试

从 A/B 的第一次成功运行中冻结去重结果。普通总结提示词和证据约束提示词使用完全相同的检索结果生成回答。两位评审分别检查每条事实性陈述是否被 `ContentText` 支持、是否绑定正确的 `source_id`。

## 样本与重复

- 8 个合成的大学生教育和职业选择案例；
- 每个 Oracle/B2 案例 4 条 query；
- 每条 query 请求 10 条结果；
- 独立运行 3 次，随机化调用顺序；
- 正式人工标注第一次运行中去重后的 Top 5；
- 两位评审先共同试标 10 条，统一尺度后再独立标注。

Oracle 组预计调用量为 `8 × 4 × 3 = 96` 次。

## 人工标注规则

### relevance

- 0：只有词面重合或完全无关；
- 1：讨论同类选择，但背景或问题偏离明显；
- 2：直接讨论当前选择或高度相似处境。

### lived_experience

- 0：纯观点、百科、机构宣传或新闻；
- 1：含模糊个人经验，但没有清晰选择过程或结果；
- 2：包含明确的个人背景、选择、行动、结果、感受或反思。

### evidence_sufficiency

- 0：摘要不足以支持任何具体人生经验判断；
- 1：能支持一个有限判断，但关键背景或结果缺失；
- 2：能支持至少一个清楚的“选择—结果/代价”关系。

### usable

当且仅当三个评分都不低于 1 时标记为 `true`。

### path_label

根据摘要实际呈现的路径自由填写，不强迫无法归类的内容进入预设标签。

## 指标

自动指标：

- HTTP 成功率和业务成功率；
- Wilson 95% 置信区间；
- 响应结构有效率和必要字段缺失率；
- 空结果率；
- P50/P95 延迟；
- 平均返回条数；
- 同一案例内 URL 重复率；
- 三次运行之间的结果 Jaccard 稳定性。

人工指标：

- Usable Precision@5；
- 平均相关性、亲历性和证据充足度；
- 每个案例的独立路径覆盖数；
- 两位评审的原始一致率和 Cohen's kappa；
- 最终回答的引用覆盖率和无依据陈述率。

## 预先定义的通过标准

| 指标 | 通过阈值 |
|---|---:|
| 业务调用成功率 | >= 95% |
| 响应结构有效率 | >= 99% |
| P95 延迟 | <= 8 秒 |
| Oracle 组 Usable Precision@5 | >= 60% |
| B2 组 Usable Precision@5 | >= 50% |
| 至少获得 2 条不同有效路径的案例比例 | >= 75% |
| 必要字段可追溯率 | 100% |
| 最终回答事实性陈述引用覆盖率 | >= 95% |
| 最终回答无依据陈述率 | <= 5% |
| 双人 usable 标注 Cohen's kappa | >= 0.60 |

硬性否决条件：如果超过 25% 的案例中，Oracle 组摘要仍无法支持至少 2 条有效人生经验，判定当前搜索摘要不足以单独支撑产品。此时应收缩产品边界、申请全文能力，或使用经过许可的本地完整案例库。

## 结果解释

| Oracle | 生成 Query | 回答忠实度 | 结论 |
|---|---|---|---|
| 失败 | - | - | 接口覆盖或摘要不足 |
| 通过 | 失败 | - | Query Builder 提示词需要重做 |
| 通过 | 通过 | 失败 | 回答生成存在幻觉或结构问题 |
| 通过 | 通过 | 通过 | 闭环具备 MVP 可行性 |

## 执行纪律

- 查询全部使用合成场景，不输入真实用户隐私；
- Access Secret 只从环境变量或系统凭证库读取；
- 不把 Secret 写入参数、源码、结果文件或截图；
- 正式运行前先 dry-run 核对调用数量；
- 主实验不自动重试，原始失败率必须保留；
- 不把赞同数、结果数或排序分数解释成总体比例或成功概率；
- 每次运行记录时间、客户端版本、提示词版本、模型和随机种子。

CLI 不是本实验的前置条件。主实验直接调用官方 HTTP API，CLI 只用于后续人工抽查与交叉验证。
